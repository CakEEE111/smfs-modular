> 目标：把 DragonMineZ（龙珠超）里的卡卡罗特模型素材，做成神秘复苏（smfs 1.5.0）框架内的一只可控厉鬼。
> 本文所有框架结论均来自 smfs 1.5.0 的反编译源码（`reference/smfs-1.5.0-src`），素材结论来自对 `dragonminez-2.1.3.jar` 的实测。

## 2. 素材清单与迁移映射

DragonMineZ 里跟 `goku` 相关的模型有 7 个、动画 1 个、贴图十余张，真正能凑成一套 GeckoLib 三件套的只有 `master_goku`。我们只需要这 3 个文件：

| 源文件（jar 内） | 目标路径（本工程） | 说明 |
|---|---|---|
| `assets/dragonminez/geo/entity/master/master_goku.geo.json` | `assets/smfsaddon/geo/entity/kakarot_ghost.geo.json` | 模型（64×64 / 46 骨骼） |
| `assets/dragonminez/textures/entity/master/master_goku.png` | `assets/smfsaddon/textures/entity/kakarot_ghost.png` | 贴图 64×64 |
| `assets/dragonminez/animations/entity/master/master_goku.animation.json` | `assets/smfsaddon/animations/kakarot_ghost.animation.json` | 动画（仅 idle / walk） |

迁移时**只需要改文件路径，不用改文件内容**（原因见 §3.5）。

同系列还有 `saga_goku` / `saga_goku_ssj` / `saga_goku_ssj2` / `saga_goku_ssj3` 等变体模型（同样是骨架 `waist`/`right_arm` 体系），但**它们没有各自的动画文件**。`animations/entity/sagas/saga_base.animation.json` 虽然有 61 个动画（含 `ki_kame` 龟派气功、12 个攻击动作），但它用的是另一套骨架，**套不上任何随包发布的模型**——详见 §3.7。

超赛形态如果以后要做，直接换 geo + 贴图，复用同一份动画即可（骨骼名一致）。

## 3. 素材实测数据与框架约束

### 3.1 模型实测

| 项 | 值 | 影响 |
|---|---|---|
| 格式 | `format_version 1.12.0`，identifier 为 `geometry.unknown` | 无需修改，见 3.5 |
| 贴图 | 64×64，衣服/头发/肤色已烘焙进图 | 无需额外护甲层 |
| 骨骼 | 46 根：`waist`(根) → `head` / `body` / `right_arm` / `left_arm`；`right_leg` / `left_leg` 为根级；`gokucabello` + `pelo1~34` 挂在 `head` 下 | 头发跟随头部转动 |
| 包围盒 | 16 × 40.5 × 10.7（Bedrock 单位）≈ **1.0 × 2.53 × 0.67 格** | 碰撞箱要调高 |
| 朝向 | 右臂 pivot `x=-5`，与 vanilla 玩家模型一致，面朝 -Z | 不需要额外 Y 轴旋转修正 |

**结论：实体碰撞箱应设为约 `0.7 × 2.5`，渲染缩放保持 1.0。**

### 3.2 动画实测（**最大缺口**）

`master_goku.animation.json` 里只有 **2 个动画**：

| 动画名 | loop | 涉及骨骼 |
|---|---|---|
| `idle` | true | waist, arms, legs… |
| `walk` | true | waist, right_arm, right_forearm, left_arm, left_forearm, right_leg, right_knee, left_leg, left_knee |

而 smfs 的 `GhostEntity` **硬性依赖三个动画名**（`GhostEntity.java:156-158`）：

```java
private static final RawAnimation WALK_ANIM   = RawAnimation.begin().thenLoop("walk");
private static final RawAnimation IDLE_ANIM   = RawAnimation.begin().thenLoop("idle");
protected static final RawAnimation ATTACK_ANIM = RawAnimation.begin().thenLoop("attack");
```

→ **`attack` 缺失**。GeckoLib 4.2.4 的实际行为（`AnimationProcessor.java:45`）：找不到动画就打印
`Unable to find animation: attack for ...` 并返回 null 队列，`AnimationController.setAnimation()` 收到 null 后 `stop()`。

结果：**不崩、但攻击时模型保持 idle/walk 姿态，同时控制台每挥一次手刷一行报错。**

→ **决策：不补攻击动画**（需求方确认"只要技能和袭击有动作，甚至只要特效也可以"）。
改为 `handleAttackAnimations` 直接返回 `PlayState.STOP`（顺带消掉报错），攻击观感全部交给粒子特效，详见 §6。

### 3.3 渲染接入点：优先用 `CustomGhostModelProvider`

`GhostEntity` 的默认渲染器 `UniversalGhostRenderer` 内部**专门为附属模组留了接口**（`client/renderer/UniversalGhostRenderer.java:36/76/120`）：

```java
if (animatable instanceof CustomGhostModelProvider provider) {
    return provider.getModelPath();      // 模型 → 贴图 → 动画，三处都是这个判断
}
```

并且 `render()` 里会读 `provider.getScale()` 做缩放（第 159 行）。

**所以最省事的路径是：实体类实现 `CustomGhostModelProvider`，然后只注册一行 `RendererType.UNIVERSAL`。**
不需要自己写 `GeoModel`，也不需要 `ResourceProvider`。

> 对比：`registerWithCustomResources` 也能用，但它适合"同一实体按状态换贴图"；我们这里是固定资产，用 `CustomGhostModelProvider` 更直接。
> 另外**千万别用** `registerWithSimpleResources` —— 它把命令空间写死成 `"smfs"`，附属模组传路径必然 404。

### 3.4 玩家侧鬼域：**做不到**（硬约束）

`GhostDomainManager` 判定"玩家能开什么鬼域"是**硬编码字符串匹配**（第 1004~1275 行）：

```java
return PlayerEvents.hasGhostType(player, "silent_ghost_eye");
return PlayerEvents.hasGhostType(player, "ghost_fire");
return PlayerEvents.hasGhostType(player, "box_ghost");
// ... 全部是 if (hasGhostType("具体鬼种")) 的硬编码
```

自定义的 `kakarot_ghost` 不在任何分支里 → **玩家驾驭它开不出鬼域**。

**应对**：走"实体侧鬼域"——`GhostEntity` 自己的 `hasGhostDomain / domainLevel / domainRadius` 独立生效，
在半径内通过重写 `applyDefaultEffects(PlayerEntity)` 给玩家上 debuff，效果等价于"卡卡罗特的气焰领域"。
这条路完全够用，也是本体 `GhostEntity` 的既有机制（`GhostEntity.java:576`）。

### 3.5 模型 identifier 不用改（已验证）

smfs 自己的模型文件 identifier **也全是 `geometry.unknown`**（实测 `child_ghost.geo.json`、`ganshibride_ghost.geo.json` 等均是），
且能正常渲染 → GeckoLib 4 在 identifier 不匹配时会回退到文件内第一个 geometry。
**所以 `master_goku.geo.json` 内容一个字都不用改。**

### 3.6 技能系统：1.5.0 无扩展点

`GhostSkillSystem` 里技能类型全是 `public static final String SKILL_TYPE_XXX` 常量 + 硬编码分支，**没有注册 API**。
自定义鬼要放技能（龟派气功），只能由附属模组自建：`KeyBinding` → 自定义 C2S 包 → 服务端处理。
这部分工作量最大，建议放到第二阶段。

### 3.7 ⚠️ 已排除：`saga_base.animation.json` 用不了

`animations/entity/sagas/saga_base.animation.json` 是最诱人的一份资产 —— 61 个动画，包含：

```
attack1_1~attack3_4 (12个攻击)  ki_kame (龟派气功)  ki_blast  ki_barrage
ki_finalflash  ki_bigbang  ki_makanko  transformation_1~3  fly  run1~5  idle/walk
```

但实测**不能用**，原因：

| 检查项 | 结果 |
|---|---|
| 该动画使用的骨骼 | `chest`、`lower_body`、`rightArm`(驼峰)、`left_shoulder`、`capa`、`cape*`、`*_wing` 等 53 根 |
| `master_goku.geo.json` 的骨骼 | `waist`、`body`、`right_arm`(下划线)、`head`、四肢，共 46 根 |
| 交集 | 仅 `waist`、`body`、`head`、`left/right_arm`、`left/right_forearm`、`left/right_leg`、`left/right_knee` |
| 全 jar 扫描 | **0 个模型**同时包含 `chest` + `lower_body` |

结论：这套动画对应的是一个**未随包发布（或被移除）的模型骨架**，是残留资产。
硬套的结果是躯干和腿会动、而手臂因为命名是 `rightArm`/`leftArm`（驼峰）而完全匹配不上 `right_arm`/`left_arm`，动作会严重走形，比不加动画更难看。

→ **放弃复用，attack 动画自己写（§6）。**
→ 龟派气功的动画同理，需要自己 K 帧。

## 4. 设计方案

### 4.1 定位

| 项 | 设定 | 理由 |
|---|---|---|
| 鬼类型 ID | `kakarot_ghost` | 与物品 `getGhostType()` 必须一致 |
| 中文名 | 卡卡罗特鬼 | |
| 恐怖等级 | **S** | 龙珠主角的牌面；也是本体最高档 |
| 定位 | 超规格"魔王级"厉鬼 | 用高复苏速度平衡强度 |

### 4.2 实体数值

`GhostEntity` 提供 10 参数构造器（`GhostEntity.java:611`），可直接指定全部战斗数值：

```java
super(type, world,
      true,    // 有鬼域
      3,       // 鬼域等级
      12.0D,   // 鬼域半径
      'S',     // 恐怖等级
      3200,    // 灵异强度（默认 1000）
      180,     // 灵异伤害（默认 100）
      160,     // 灵异抗性（默认 50）
      0.5F);   // 恢复因子（默认 0.2，越高复苏越快）
```

设计意图：

- 灵异强度 3200 = 3.2 倍本体标准鬼，符合 S 级。
- 恢复因子 0.5（默认 0.2 的 2.5 倍）→ **复苏速度显著更快**，玩家驾驭它风险极高，形成"强力但短命"的张力。
- 鬼域半径 12 格（本体常见 5~8），对应气焰范围压制。

### 4.3 容器物品数值

| 参数 | 值 | 对应 |
|---|---|---|
| maxSpiritBonus | 2000 | 灵力上限 |
| spiritResistanceBonus | 80 | 灵异抗性 |
| spiritDamageBonus | 200 | 灵异伤害 |
| sanityBonus | 0 | 理智（不补，保持恐怖感） |
| revivalFactor | 0.6 | 复苏系数 |

对比本体标准容器（如食物鬼 800/50/60/0/0.3），卡卡罗特是 2.5 倍强度、2 倍复苏压力。

### 4.4 刷新规则

```java
GhostSpawnAPI.registerGhostSpawn(TYPE, "kakarot_ghost", 10, 5, 24000, true);
```

参数语义（`GhostSpawnManager.java:131`，已确认）：

- `minDay=10` —— 第 10 天（游戏内）后才可能出现
- `spawnChance=5` —— **百分比**，0~100，越界会被夹紧
- `spawnInterval=24000` —— **tick**，24000 = 1 游戏日
- `nightOnly=true` —— 仅夜晚

对比 3 参数重载的默认值（80% / 24000 / 仅夜晚），我们把概率压到 5%，做成"稀有事件"。

### 4.5 鬼域效果（实体侧）

重写 `applyDefaultEffects(PlayerEntity player)`，在 `isInGhostDomain(player)` 为真时施加：

- 反胃（NAUSEA）—— 本体通用压迫感
- 缓慢 / 虚弱 —— 气焰压制
- 可选：自定义 buff（如需"气焰灼烧"需额外注册 StatusEffect）

本体最简写法可直接抄 `entity/ghost/FogGhostEntity.java`：

```java
@Override
protected void applyDefaultEffects(PlayerEntity player) {
    player.addStatusEffect(new StatusEffectInstance(
            StatusEffects.NAUSEA, Integer.MAX_VALUE, getGhostDomainActualLevel() - 1, false, false));
}
```

`getGhostDomainActualLevel()` 是父类方法，取的是"考虑玩家个人设置后的实际鬼域等级"，用它算 buff 强度最稳。

## 6. 特效方案（替代攻击动画）

需求方确认：**不做挥拳动画，攻击和技能只要有动作或特效即可**。于是攻击观感全部由粒子承担。

### 6.1 关掉缺失动画的报错

实体里覆写攻击动画钩子，直接返回 `PlayState.STOP`：

```java
@Override
protected PlayState handleAttackAnimations(AnimationState<GhostEntity> state) {
    return PlayState.STOP;
}
```

作用：不再向 GeckoLib 请求不存在的 `attack`，控制台不再刷 `Unable to find animation: attack`。

副作用（已知、可接受）：`executeAttack` 会把 `handSwinging` 置真，而父类的
`handleMovementAnimations` 在 `handSwinging` 为真时返回 `STOP`，所以挥拳那 4~5 tick
`idle`/`walk` 会暂停 —— 观感上像一次短暂的"顿帧"，配合粒子反而像打击停顿。

### 6.2 三层特效

| 层 | 触发点 | 实现 |
|---|---|---|
| **鬼域气焰** | 每 3 tick 常驻 | `tick()` 里沿身体随机角度撒金色 dust + 偶尔 `ELECTRIC_SPARK` |
| **出拳气浪** | 每次攻击 | `executeAttack` 里在正前方 1 格炸开青白 dust + 电火花 |
| **命中冲击** | 玩家距离 < 4 格 | 玩家身上 18 颗金色 dust + 6 颗 `SOUL` + 暴击音效 + 轻爆炸音 |

关键 API（1.20.1 / yarn）：

```java
// 彩色粒子：DustParticleEffect(Vector3f, scale)，注意是 Vector3f 不是 (r,g,b)
new DustParticleEffect(new Vec3d(1.0, 0.82, 0.12).toVector3f(), 1.6f);

// 服务端生成粒子
world.spawnParticles(effect, x, y, z, count, dx, dy, dz, speed);

// 取实体前方：Vec3d.fromPolar(0, yaw).multiply(距离)
Vec3d front = this.getPos().add(Vec3d.fromPolar(0f, this.getYaw()).multiply(1.0));
```

本体还自带一个现成的灵异粒子方法，可直接调用：

```java
PlayerEvents.spawnSpiritDamageParticles(GhostEntity ghost);   // 15 颗灵异粒子 + 音效
```

### 6.3 如果以后想要真动画

模型骨骼 `right_arm` pivot `[-5, 22, 0]`、父级 `waist`，绕自身 X 轴负向旋转就是向前挥拳。
在动画 JSON 里加一个 `attack` 键、删掉 `handleAttackAnimations` 的覆写即可回退到动画方案。
两者可以并存：有动画时优先播动画，粒子照常叠加。

## 7. 超赛变身

**触发**：主鬼是卡卡罗特且鬼等级达到 **10 级**，按 `R` 切换。**随开随放** —— 没有冷却，也没有固定时长，
按一次开、再按一次关（或死亡）。代价体现在持续消耗上：变身期间每秒 +2 复苏度。

### 7.1 ⚠️「等级」和「复苏度」是两套独立数值

这是设计上最容易搞错的地方，我第一版就搞错了：

| 数值 | 含义 | 范围 | 读取方式 |
|---|---|---|---|
| **等级** | 鬼的培养等级，本体面板显示为"等级: 10" | 1 ~ 10 | `PlayerEvents.getGhostSlotLevel(player, slot)` |
| **复苏度** | 复苏进度条，本体面板显示为"复苏程度: 2/1000" | 0 ~ 1000，满值即死 | `getGhostSlotRevivalDegree` / `getRequiredRevivalDegree` |

两者**互不换算**。玩家实际可能"等级 10、复苏度 2/1000"——满级但几乎没复苏。
最初的实现把门槛写在复苏度上（要求 ≥900），结果这类玩家永远变不了身。

**现在的判定直接复用本体的等级参数**，不自己算：

```java
GhostDomainManager.canUseGhostSkill(player, "kakarot_ghost", ITEM, 10)
//                                            requiredLevel ↑ 本体内部会走 getEffectiveSkillLevel 比较
```

返回 `LEVEL_TOO_LOW` 时提示会带出当前等级，方便对账。
复苏度不再是门槛，而是**变身的代价**（见 7.3）。

### 7.2 实现结构

| 文件 | 职责 |
|---|---|
| `effect/SuperSaiyanEffect.java` | 变身 buff：属性修正 + 气焰粒子 + 每秒烧复苏度 + 退场虚弱 |
| `network/KakarotTransformPacket.java` | C2S 请求包 + 服务端四重校验 |
| `client/SmfsAddonClient.java` | `R` 键绑定，按下即发包 |
| `SmfsAddon.java` | 注册 `Registries.STATUS_EFFECT` |

用 **StatusEffect** 而不是自己记 NBT 的原因：属性修正由原版 `AttributeContainer` 托管，
效果结束自动回滚，不会污染玩家存档。

### 7.3 数值

| 项 | 值 |
|---|---|
| 灵异伤害 | **NBT ×50** + 属性 `MULTIPLY_TOTAL +49` |
| 最大灵异强度 | **NBT ×50** |
| 当前灵异强度 | **NBT ×50** |
| 灵异抗性 | **NBT ×50** + 属性 `+50` |
| 护甲 | `+50` |
| 移速 | `MULTIPLY_TOTAL +0.30`（**不是 ×50**，否则操作不了） |
| 击退抗性 | `+0.5` |
| 持续时间 | 常驻（`Integer.MAX_VALUE`），按 R 关闭 |
| 冷却 | 无 |
| 复苏代价 | 每秒 **+2** 点 |

> 移速没有按 50 倍放大 —— 0.7×50 = 35 格/tick，人物会直接穿模飞出世界。
> 要改就动 `EntityAttributes.GENERIC_MOVEMENT_SPEED` 那行。

复苏度上限**卡在 `required - 1`**（999），避免在变身中途被直接判死。

### 7.3.1 ⚠️ 为什么 ×50 必须写进 NBT

这是本项目最隐蔽的一个坑。

- **属性修正**（`AttributeModifier`）只影响 `EntityAttributeInstance.getValue()`，
  用于原版伤害、移速、护甲、UI 面板；
- 但**打鬼时本体读的是 NBT**：`GhostEntity#damage` 里 `PlayerEvents.getSpiritAttributes(player).getDouble("spiritDamage")`，
  完全不看属性实例。

也就是说：只加 `AttributeModifier` 的话，面板数字变漂亮了，**打鬼伤害一点没涨**。

受影响的 NBT 字段（`SCALED_KEYS`）：

| 字段 | 对应 HUD |
|---|---|
| `spiritDamage` | 打鬼伤害 |
| `maxSpirit` | 最大灵异强度 |
| `currentSpirit` | 当前灵异强度 |
| `spiritResistance` | 灵异抗性 |

所以 `onApplied` 里把这一整组一起备份并放大：

```java
NbtCompound spirit = PlayerEvents.getSpiritAttributes(player);   // 注意：这是 copy
NbtCompound backup = new NbtCompound();
for (String key : SCALED_KEYS) {
    double original = spirit.getDouble(key);
    backup.putDouble(key, original);
    spirit.putDouble(key, original * 50.0);
}
spirit.put(BACKUP_KEY, backup);
PlayerEvents.setSpiritAttributes(player, spirit);                // 必须写回
```

`getSpiritAttributes` 返回的是 **copy**，改完必须 `setSpiritAttributes` 写回，否则无效。
写回时本体内部会 `sendSpiritDataToClient`，所以 HUD 会**立刻**显示放大后的数字（HUD 读的正是 NBT）。

### 7.3.2 崩溃兜底

直接改 NBT 是有风险的：服务器如果在变身期间崩溃，放大的 50 倍会跟着存档走，
玩家就永久 50 倍了。

所以做了三层保护：

| 时机 | 动作 |
|---|---|---|
| `onRemoved` | 读取 `BACKUP_KEY`（NbtCompound）逐字段还原并删除备份 |
| 玩家上线（`ServerPlayConnectionEvents.JOIN`） | 若「有备份但没在变身」，判定为残留，自动还原并打 warn 日志 |
| 备份键名 | `smfsaddon_ssj_backup`，与本体字段不冲突 |

### 7.3.3 金色头发（FeatureRenderer 叠加层）

试了四种做法，前三种都不成立，全部记录在这里：

| 方案 | 结果 |
|---|---|
| 挂在鬼实体 `getTexturePath()` | ❌ 变身效果在玩家身上，鬼实体拿不到状态，纯死代码 |
| 整张皮肤替换成超赛皮肤 | ❌ 身体和衣服也一起变了，不是"只换头发" |
| 运行时把金发合成到原皮肤 | ❌ 玩家皮肤是 `PlayerSkinTexture extends ResourceTexture`，加载后 NativeImage 即丢弃，取不到像素 |
| 在 `render` 的 `TAIL` 自己画 hat | ❌ 能在错误的位置画出一大块黑块（见下） |
| **注册 FeatureRenderer** | ✅ 采用 |

#### 踩坑：为什么不能在 `render` 末尾画

`LivingEntityRenderer#render` 内部的模型空间变换是在方法内 push/pop 的：

```java
matrices.push();
this.setupTransforms(...);
matrices.scale(-1.0F, -1.0F, 1.0F);
this.scale(entity, matrices, tickDelta);
matrices.translate(0.0F, -1.501F, 0.0F);
this.model.render(...);       // ← 模型在这里被画出来
...
matrices.pop();               // ← 变换在这里被还原
```

在 `TAIL` 注入时，`pop()` 已经执行完，此时矩阵只剩"实体变换"。
拿这个矩阵去画 `model.hat`，坐标原点落在**玩家脚下**，尺度也是错的 ——
表现就是一大块黑黢黢的方块糊在人物身上，周围飘着碎片。

#### 正确做法：FeatureRenderer

`FeatureRenderer` 由 `LivingEntityRenderer` 在**模型空间内**回调，矩阵状态与
`model.render` 完全一致，画出来的东西天然贴合头部。

```java
public class SsjHairFeatureRenderer extends FeatureRenderer<AbstractClientPlayerEntity, PlayerEntityModel<AbstractClientPlayerEntity>> {
    @Override
    public void render(MatrixStack matrices, VertexConsumerProvider vertexConsumers, int light,
                       AbstractClientPlayerEntity entity, ..., float headYaw, float headPitch) {
        if (!entity.hasStatusEffect(SmfsAddon.SUPER_SAIYAN)) return;

        // 具体画法交给 GeckoLib，见下一节；head 传玩家模型的头部部件，头发才能跟着转
        SsjHairGeoRenderer.get().renderHair(matrices, vertexConsumers,
                LightmapTextureManager.MAX_LIGHT_COORDINATE, this.getContextModel().head);
    }
}
```

注册靠一个只做"挂图层"的 mixin（继承目标类是为了拿到 protected 的 `addFeature`）：

```java
@Mixin(PlayerEntityRenderer.class)
public abstract class PlayerSsjHairMixin extends LivingEntityRenderer<...> {
    @Inject(method = "<init>(Lnet/minecraft/client/render/entity/EntityRendererFactory$Context;Z)V", at = @At("TAIL"))
    private void smfsaddon$addHairLayer(EntityRendererFactory.Context ctx, boolean thinArms, CallbackInfo ci) {
        this.addFeature(new SsjHairFeatureRenderer(this));
    }
}
```

#### 两个渲染层的坑

| 表现 | 原因 | 处理 |
|---|---|---|
| 玩家被一大团**黑块**罩住 | 几何画对了，但用的是传入的 `light`，鬼域环境光极暗 → 整块渲染成黑色 | 光照强制 `LightmapTextureManager.MAX_LIGHT_COORDINATE` |
| 换成自发光层后**什么都看不见** | emissive 层开启背面剔除，而模型空间带 `scale(-1,-1,1)` 镜像，面朝向反转 → 全被剔除 | 保留 `getEntityCutoutNoCull`（不剔除），只改光照 |

结论：**层要 NoCull，光照要满**，两者缺一不可。

```java
RenderLayer layer = RenderLayer.getEntityCutoutNoCull(TEXTURE);   // 不剔除
VertexConsumer buffer = buffers.getBuffer(layer);
// light 传 LightmapTextureManager.MAX_LIGHT_COORDINATE
```

#### 头发几何与贴图：直接用龙珠模组的（方案 B：交给 GeckoLib）

手画的 8×8 像素刘海太糙，改成搬运原模型。素材只有两个：

| 要素 | 来源 |
|---|---|
| 几何 | `kakarot_ghost.geo.json` 中 `head` → `gokucabello` → `pelo1..34` 那条骨骼链（36 根骨骼 / 52 个立方体） |
| 贴图 | 龙珠 `saga_goku_end_ssj.png`（超赛金发版，头发区 `#FFE59D`） |

先试过"方案 A：把几何拍平成 `ModelPart`"，能出图但到处都是坑，最终放弃。放弃的理由是**本质性的**：

- Bedrock 的每个立方体都带 `rotation`（绕自身最小角），而 MC 的 `ModelPart` 只有骨骼级旋转。
  方案 A 只能给每个立方体单开一个子部件、把枢轴放到它的最小角来硬凑，
  于是 52 个立方体变成 52 个根部件，**父子层级全丢**（`pelo14` 的旋转本应带动它的子骨头）；
- 立方体还要自己乘 `24 - y - height` 的换算、旋转还要按镜像取负（y 轴镜像后绕 X/Z 取反，
  **绕 Y 不取反**——这个也错过一次），错一处就是一撮毛飘在脸外；
- 结果是"能看但不像"，用户原话是"这头发跟龙珠模组的不太一样"。

最终做法是**方案 B：把 geo 原封不动抠出来，让 GeckoLib 自己解析自己画** ——
也就是龙珠模组自己的做法。这样骨骼层级、立方体级旋转、法线明暗、UV 展开全部由
GeckoLib 的原生管线负责，我们只负责摆正坐标系。

**落地文件**：

| 文件 | 作用 |
|---|---|
| `assets/smfsaddon/geo/entity/ssj_hair.geo.json` | 从 `kakarot_ghost.geo.json` 抠出的头发子模型，`geometry.ssj_hair`，`head` 枢轴保留 `(0,24,0)` |
| `assets/smfsaddon/textures/entity/ssj_hair.png` | 龙珠 `saga_goku_end_ssj.png` 原样拷贝 |
| `client/SsjHairGeoRenderer.java` | 极简 `GeoRenderer<GhostEntity>` 实现，只在 `renderHair()` 里画一遍 |
| `client/SsjHairFeatureRenderer.java` | 变身判定 + 调用上面那个 |

`GeoRenderer` 在 GeckoLib 4.2.4 有 4 个必须实现的钩子，少一个都编译不过：

```java
public void updateAnimatedTextureFrame(GhostEntity a) {}                        // 没有动画贴图，留空
public void fireCompileRenderLayersEvent() {}                                   // 没有额外渲染层，留空
public boolean firePreRenderEvent(MatrixStack, BakedGeoModel, VertexConsumerProvider, float, int) {
    return true;   // ← 返回值是 boolean，不是 void！返回 true = 放行渲染
}
public void firePostRenderEvent(MatrixStack, BakedGeoModel, VertexConsumerProvider, float, int) {}
```

#### 坐标系换算（这一节是全部痛苦的来源）

geo 是 **Bedrock 空间**：y 向上、单位 1/16、骨骼与立方体都用**绝对坐标**。
而 `FeatureRenderer.render` 拿到的矩阵是 **MC 模型空间**：y 向下、头颈在 y=0。
两者之间的映射是三次反射：

```
y' = -y + 1.5     Bedrock y 向上 → MC y 向下；+1.5 把颈部 24/16 抬到 0
x' = -x           GeckoLib 烘焙时已对 x 取负（BakedModelFactory: origin = -(x+size)/16），渲染时再取负还原
z' = z            Z_FLIP：早期翻过，实测这版几何不需要翻；翻与不翻决定刘海在脸前还是脑后
```

`Y_OFFSET` 的推导（验算而不是试出来的）：
Bedrock 里颈部 `y=1.5`、头顶 `y=2.0`；MC 里颈部 `y=0`、头顶 `y=-0.5`。
设 `y' = -y + c`，代入颈部 `0 = -1.5 + c` → `c = 1.5`；验算头顶 `-2.0 + 1.5 = -0.5` ✓

代码长这样（常量对应几个反射与偏移，出问题只改一个数）：

```java
private static final float Y_OFFSET = 1.5f;    // 垂直对齐，正值下移
private static final float Z_OFFSET = 0.0f;    // 前后位移（不是翻转，别用这个修"刘海在后面"）
private static final boolean Z_FLIP = false;   // 前后翻转；实测这版关掉才对

matrices.push();
if (head != null) head.rotate(matrices);               // ← 先套头部变换（绕颈部）
matrices.translate(0.0f, Y_OFFSET, Z_OFFSET);          // ← 再 translate
matrices.scale(-1.0f, -1.0f, Z_FLIP ? -1.0f : 1.0f);   // ← 最后 scale
for (GeoBone bone : baked.topLevelBones())
    renderRecursively(matrices, null, bone, layer, buffers, buffer, false,
            0.0f, light, OverlayTexture.DEFAULT_UV, 1f, 1f, 1f, 1f);
matrices.pop();
```

#### 坐标系的坑（全部踩过，一条一条来）

| 表现 | 真正原因 | 处理 |
|---|---|---|
| 头发**整块贴在脚下**，人在里面是黑的 | 在 `render` 的 `TAIL` 画，模型矩阵已 pop | 换 `FeatureRenderer` |
| 头发**不跟随头部**（转头它不动、低头它不动，或绕错点乱飘） | 给 geo 里的 `head` 骨骼设 `rotX/rotY`，但那根骨骼的 pivot 变换后不在颈部，等于绕一个错的点转 | 把 `model.head` 的变换套在外层（`head.rotate(matrices)`），用 MC 自己的 pivot |
| 整体**高了一个头** | 平移量被 `scale` 一起取反了（`y' = -(y+1.5)` 而不是 `-y+1.5`） | **先 translate 后 scale** |
| 头发**跑到胸口** | 又多补了一次 `head` 骨骼的 `(0,24,0)` 枢轴。GeckoLib 的 pivot 是绝对坐标，靠 `translateToPivotPoint` / `translateAwayFromPivotPoint` 互相抵消，整棵树本来就在同一空间里 | 删掉多余的 pivot 偏移 |
| 第三人称下**移动方向与头发方向相反**（x 轴镜像） | GeckoLib 烘焙时对 x 取负，我们没还原 | `scale(-1,-1,1)` |
| **前后反了**：刘海跑到脑后，后脑的毛盖在脸上 | z 轴多翻了一次 | `Z_FLIP = false`（实测这版不翻才对；换模型/贴图后若又反了，改回 true） |

#### 曾经常用的「符号补偿」，现在不需要了

早先在 `renderHair` 里手动给骨骼设角度时，因为 `scale(-1,-1,-1)` 是反射
（行列式 -1），会把绕 x、绕 y 的旋转方向一起反掉，所以要用
`PITCH_SIGN` / `YAW_SIGN` 两个常数把它补偿回来，调到眼花。

现在旋转交给 `model.head.rotate(matrices)`，那是在**镜像之外**施加的，
不存在符号问题，两个常数已经删掉。以后若再看到「向左看、头发向右转」，
不要加符号，先检查是不是又退回了手动设骨骼旋转。

### 7.4 开启条件（服务端）

```java
canUseGhostSkill(player, "kakarot_ghost", KAKAROT_GHOST_ITEM, 10)   // 主鬼 + 等级 10
```

只有这两条。**没有冷却、没有时长限制** —— 已经在变身时会走 `removeStatusEffect` 直接关闭。
关闭不收任何费用，代价只在"开着的时候"逐秒扣除。

冷却直接复用了本体的 `GhostDomainManager.checkAndSetJSkillCooldown`，
自带"冷却中，剩余 x.x 秒"的提示，不用自己写。

### 7.5 ⚠️ 一个实测出来的注意点

**灵异抗性这一项大概率不生效。**

- 进攻侧：`PlayerEntityMixin#getSpiritDamage()` 读的是属性实例 `getValue()`（含修正），所以 **+150% 伤害是真实生效的**。
- 防御侧：`PlayerEvents.handleSpiritDamage()` 读的是 **NBT** 里的 `spiritResistance`，
  不是属性实例，所以 StatusEffect 加的修正进不去这条路径。

保留这个修正没有副作用（万一有别的路径读实例），但**不要指望它减伤**。
要真做减伤，得直接改 NBT 并在效果结束时回滚 —— 风险是玩家中途死亡会导致 NBT 残留，暂不实现。

## 8. 龟派气功（C 键）

### 8.1 释放流程：完全照抄本体技能包

本体所有技能包（如 `ClientCandyGhostJSkillC2SPacket`）都是这个结构，我们逐行对齐：

```java
// 1) 主鬼校验
SkillCheckResult r = GhostDomainManager.canUseGhostSkill(player, "kakarot_ghost", ITEM, -1);
if (r == NO_GHOST)       { msg; return; }
if (r == LEVEL_TOO_LOW)  { msg; return; }

// 2) 冷却（本体系统，自带"冷却中，剩余 x 秒"提示）
if (!GhostDomainManager.checkAndSetJSkillCooldown(player, KEY, TICKS, "龟派气功")) return;

// 3) 执行
fire(player);

// 4) 复苏度结算 —— 本体技能的真正成本
PlayerEvents.balanceRevivalDegree(player);
```

### 8.2 ⚠️ 本体技能不消耗灵力

这是最初版本放不出来的根因。

- 玩家 `currentSpirit` **默认值是 0**（`PlayerEvents` 里 `putDouble("currentSpirit", 0.0)`），靠时间缓慢恢复；
- 而本体**任何一个技能都不扣灵力** —— `GhostDomainManager` / `GhostSkillManager` 里搜不到 `setCurrentSpirit`；
- 所以最初写的"消耗 300 灵力"是自创门槛，玩家灵力不足时直接被拦下。

**现在的成本模型与本体一致**：`PlayerEvents.balanceRevivalDegree(player)`
内部是"涨 20、降 8"，即**每次释放净 +12 点复苏度**。技能靠复苏度付费，不靠灵力。

### 8.3 参数

| 项 | 值 | 说明 |
|---|---|---|
| 按键 | `C` | 原版 `F` 是副手交换，本体已占 J/K/G/N/V |
| 冷却 | 20 tick（1 秒） | 与本体所有技能完全一致 |
| 射程 | 32 格 | 被方块挡住会提前截断 |
| 伤害 | (120 + 灵异伤害 × 0.5) × 等级系数 | 等级系数 = 1 + (鬼等级-1)×0.25，10 级为 ×3.25 |
| 成本 | 每次 +12 复苏度 | 本体 `balanceRevivalDegree` |

### 8.4 ⚠️ 伤害结算：`GhostEntity` 只认"玩家 + 技能标记"

这是最容易踩的坑，第一版就是这里出的问题 —— **对鬼完全零伤害**。

`GhostEntity#damage()` 第一件事就是看伤害源的来源实体：

```java
if (source.getSource() instanceof GhostEntity attackerGhost) { ... 鬼打鬼 ... }
else if (source.getSource() instanceof GhostMasterEntity gm) { ... 驭鬼者 ... }
else if (source.getSource() instanceof PlayerEntity player) {
    boolean isSkillDamage = GhostSkillManager.isSkillDamage(source);  // ← 关键
    if (!isSkillDamage) { /* 没有灵异武器/尸油/灵异奔涌 → return true 直接吞掉 */ }
    ...
}
```

而 `GhostSkillManager.isSkillDamage(source)` 的实现是：

```java
return source.getSource() instanceof PlayerEntity player && ModEvents.processingSpiritDamage.get();
```

**两个条件缺一不可。** 最初用的是 `ModDamageSources.ghost(world)` —— 这个源没有来源实体，
三个分支全不匹配，伤害被本体静默丢弃，连提示都没有。

正确写法：

```java
ModEvents.processingSpiritDamage.set(true);
try {
    target.damage(player.getDamageSources().playerAttack(player), damage);
} finally {
    ModEvents.processingSpiritDamage.set(false);
}
```

`ModEvents` 里 `ALLOW_DAMAGE` 的回调也印证了这个语义：

```java
if (processingSpiritDamage.get()) {
    return true;      // 放行，跳过所有伤害源过滤
}
```

所以打上标记后对普通生物同样安全 —— 只是跳过过滤，不改变数值。

### 8.5 ⚠️ 对鬼的实际伤害不由 `amount` 决定

打到鬼身上后，本体**忽略传入的 `amount`**，改用玩家自己的灵异属性重算：

```java
effectiveSpiritDamage = weaponBonus + totalSpiritDamage * 0.5F;   // 无灵异武器时倍率固定 0.5
actualDamage = PlayerEvents.calculateSpiritDamage(effectiveSpiritDamage, 鬼的灵异抗性);
```

其中 `totalSpiritDamage` 读的是玩家 NBT 里的 `spiritDamage`（即装备/驾驭鬼带来的灵异伤害）。

以本附属的容器为例：基础 10 + 容器 +200 ≈ 210 → 有效值 105；
打灵异抗性 100 的鬼 → `105² / (105+100) ≈ 54` 点。
开超赛（灵异伤害 ×2.5）后 525 → 有效 262 → `262²/(262+100) ≈ 190` 点。**变身对龟派气功是实打实的加成。**

另外本体在 `calculateSpiritDamage` 前有个 **1 秒连击衰减**（`SPIRIT_WEAPON_COOLDOWN`），
1000ms 内第二次命中会按时间比例打折 —— 我们的冷却正好 20 tick，刚好不触发衰减。

> 验证方式：本体配置里 `showActionBarInfo` 与 `showDamageText` 打开时，
> 命中鬼会在动作栏显示 `§a对 §fXX §a造成了§f N §a点灵异伤害`。

### 8.6 命中判定

```java
Vec3d start = player.getEyePos();
Vec3d dir = player.getRotationVec(1.0f);

// 方块遮挡截断射程
BlockHitResult blockHit = world.raycast(new RaycastContext(
        start, start.add(dir.multiply(32.0)),
        RaycastContext.ShapeType.COLLIDER, RaycastContext.FluidHandling.NONE, player));

// 沿射线每 0.5 格采样，用 1.4³ 的小 Box 捞活体
for (double d = 1.0; d <= limit; d += 0.5) {
    Vec3d point = start.add(dir.multiply(d));
    Box probe = new Box(point.x-0.7, point.y-0.7, point.z-0.7,
                        point.x+0.7, point.y+0.7, point.z+0.7);
    List<LivingEntity> found = world.getEntitiesByClass(LivingEntity.class, probe,
            e -> e != player && e.isAlive() && !e.isSpectator());
    if (!found.isEmpty()) { /* 命中，break */ }
}
```

用射线而不是弹道实体：不用注册 EntityType，也没有实体同步与生命周期开销。
最远 32 格 → 最多 64 次查询，单次施法可忽略。

### 8.7 平A（近战）也要能伤鬼

本体对玩家近战有一条**硬门槛**（`GhostEntity#damage` 的 PlayerEntity 分支）：

```java
if (!isSkillDamage) {
    boolean hasSpiritWeapon = SpiritWeapon.isSpiritWeapon(player.getMainHandStack());
    boolean hasCorpseOilWeapon = WeaponOilHandler.getCorpseOilLayers(...) > 0;
    if (!hasSpiritWeapon && !hasCorpseOilWeapon) {
        if (!SpiritSurgeStatusEffect.hasSpiritSurgeEffect(player)) {
            return true;          // ← 直接吞掉，连伤害数字都没有
        }
    }
}
```

也就是说**空手或用普通剑砍鬼，本体判定为"打不动"**，这是它刻意的设定：
想伤鬼必须满足三者之一 —— 手持 `SpiritWeapon`（鬼拳、锈迹柴刀等）、武器抹了尸油、或处于灵异奔涌状态。

附属的处理：复用本体自己的"技能伤害"通道，不重写伤害逻辑。

```java
AttackEntityCallback.EVENT.register((player, world, hand, entity, hitResult) -> {
    if (world.isClient() || hand != Hand.MAIN_HAND) return ActionResult.PASS;
    if (!(entity instanceof LivingEntity)) return ActionResult.PASS;
    if (!isKakarotMainGhost(player)) return ActionResult.PASS;

    ModEvents.processingSpiritDamage.set(true);   // 让这次平A走技能伤害分支
    PENDING_RESET.set(true);
    return ActionResult.PASS;
});

// 伤害在本 tick 的网络包处理中结算，Tick 末统一复位
ServerTickEvents.END_SERVER_TICK.register(server -> {
    if (PENDING_RESET.getAndSet(false)) {
        ModEvents.processingSpiritDamage.set(false);
    }
});
```

要点：

- **只对「主鬼是卡卡罗特」的玩家生效**，不影响本体其它鬼的平衡；
- 打开标记后 `ModEvents` 的 `ALLOW_DAMAGE` 会直接放行，跳过伤害源过滤 —— 这也是本体技能伤害的正常路径；
- 复位放在 `END_SERVER_TICK`，确保伤害已经结算完，不会污染同一 tick 内的其它判定；
- 伤害公式、音效、粒子全部沿用本体，没有复制任何计算。

> 副作用提醒：标记是全局 `AtomicBoolean`，同一 tick 内如果有多个玩家攻击，
> 会共用这一次"放行"。实际战斗里影响可以忽略。

## 9. 鬼域（已移除）

> **这一节保留作历史记录，功能已删。**
>
> 变身原本会给玩家挂上本体的 `GOLDEN_GHOST_DOMAIN`，并每秒向周围广播
> `applyTargetGhostDomainToOtherPlayers`。后来决定**只保留变身本身**：
> 鬼域是本体那套"压制/复苏"的循环，附属接进来会干扰玩家对鬼域来源的判断
> （分不清这只鬼域是鬼给的还是自己变身给的）。
>
> 现在变身只剩：灵异属性翻倍、金色气焰粒子、每秒烧复苏度。下面的代码
> 仅作参考，不要再照抄。

### 9.1 设计原则

**附属不自建玩法系统。** 鬼域的半径计算、目标压制、屏幕表现、配置开关全部走本体。

本体 `GhostDomainManager` 已经有完整实现，我们要做的只是"把玩家接进这套系统"：

```java
// 生效时：挂上本体的金色鬼域（视觉/夜视/客户端表现由本体负责）
player.addStatusEffect(new StatusEffectInstance(
        ModEffects.GOLDEN_GHOST_DOMAIN, DURATION_TICKS, DOMAIN_LEVEL - 1, false, false, true));

// 每秒：让本体把压制广播给半径内的其他玩家与生物
GhostDomainManager.applyTargetGhostDomainToOtherPlayers(
        player, ModEffects.GOLDEN_GHOST_DOMAIN_TARGET, DOMAIN_LEVEL);
```

`applyTargetGhostDomainToOtherPlayers` 内部替我们做了这些事：

| 本体已处理 | 说明 |
|---|---|
| 半径计算 | `getDomainRadius(player, level)`，会考虑玩家的个人设置滑条 |
| 玩家目标 | 范围内其他玩家挂 `GOLDEN_GHOST_DOMAIN_TARGET` + `LOST` |
| 生物目标 | 范围内非玩家生物同样挂 target + LOST |
| 配置开关 | 尊重 `ModConfig.enableGhostDomainEffectsOnMobs`，玩家关掉就不压怪 |
| 效果时长 | 200 tick，靠我们每秒刷新维持 |

**额外收益**：本体 `GoldenGhostDomainEffect.applyUpdateEffect` 会给鬼域主人挂 `NIGHT_VISION`
（`field_5925`），所以变身期间看得更清楚 —— 这是本体所有鬼域的既定行为，白拿。

### 9.2 为什么不做"常态鬼域"

本体里鬼域是**主动开启**的（K 键），不是常驻。而且本体的域效果是 HARMFUL 类别，
常驻会给玩家持续挂负面图标。所以这里跟本体保持一致：**变身才有鬼域，变身结束自动关闭**
（`onRemoved` 里 `removeStatusEffect(GOLDEN_GHOST_DOMAIN)`）。

### 9.3 曾经走错的路（记录）

最初的实现是自建 `KakarotDomainHandler`：`ServerTickEvents` 每秒扫 `Monster`，
自己上缓慢/虚弱、自己算半径、自己画金色气环。这套东西**已全部删除**，原因：

- 重复实现了本体已有的半径/目标/配置逻辑
- 自建压制不认本体的 `enableGhostDomainEffectsOnMobs` 配置，玩家关了也没用
- 自己画的粒子环和本体鬼域表现不统一

现在的附属里，**玩法数值一条都不自己算**，只保留体表气焰粒子作为表现层点缀。

### 9.4 附属仍然自建的部分（及原因）

| 自建内容 | 为什么不能用本体的 |
|---|---|
| 技能按键 `R` / `F` | 本体所有按键都用 `KeyBinding.wasPressed()` 轮询且**先于附属消费**（`KeyEventHandler` 在 client init 注册 EndTick）。同一个 KeyBinding 附属拿不到事件。 |
| 两个 C2S 网络包 | `GhostSkillSystem` 的鬼种是 `SKILL_TYPE_XXX` 常量 + 硬编码分支，**1.5.0 没有任何注册 API**，附属无法把自己的鬼挂进本体技能表。 |
| 一个自定义 StatusEffect | 本体的 `ModEffects` 是静态注册的，没有开放注册入口；但属性修正、效果时长回滚仍由原版 `AttributeContainer` 托管。 |
| 贴图 / 模型 / 成就 / 掉落表 | 标准资源与数据包，本来就该附属自带。 |

**除以上四项，其余全部走本体**：实体注册（`GhostAPI`）、容器绑定（`TameableItemAPI` + `BaseGhostEyeItem`）、
渲染（`UniversalGhostRenderer` + `CustomGhostModelProvider`）、刷新（`GhostSpawnAPI`）、
冷却（`GhostDomainManager.checkAndSetJSkillCooldown`）、鬼域（上面的金色鬼域）、
灵异伤害（`ModDamageSources` + `SpiritAttributes`）、属性面板数值（`PlayerEvents`）。

### 10.3 让本体界面认识我们的鬼（GhostUtils 四张表）

**这是最容易漏掉、但必须做的一步。**

不注册的后果（实测截图）：驾驭成功弹窗显示 **"未知鬼魂"**，技能列表和鬼域栏全是 **"无" / "否"**。
因为本体 `GhostAbilityPopupS2CPacket` 是拿 ghostType 去 `GhostUtils` 的两张硬编码表里查，
查不到就走 fallback。

本体其实预留了四组附属注册接口（`com.xie.smfs.util.GhostUtils`）：

| 方法 | 作用 |
|---|---|
| `registerAddonDisplayNameMapping(ghostType, String)` | 显示名。不注册 → "未知鬼魂" |
| `registerAddonAbilityMapping(ghostType, List<String>)` | 驾驭面板的技能/鬼域行 |
| `registerAddonGhostMapping(ghostType, ItemStack)` | 鬼种 ↔ 物品映射 |
| `registerAddonEntityCreationMapping(ghostType, EntityType)` | 鬼种 ↔ 实体创建 |

调用时机：**必须在物品和实体都注册完之后**（`registerAddonGhostMapping` 要用到 ItemStack）。

```java
GhostUtils.registerAddonDisplayNameMapping("kakarot_ghost", "卡卡罗特");

GhostUtils.registerAddonAbilityMapping("kakarot_ghost", List.of(
        "代号：卡卡罗特",
        "被动：气焰领域，变身时展开金色鬼域",
        "袭击：气焰冲击，命中附加金色爆发",
        "",
        "主动技能：龟派气功（F 键）",
        "",
        "临界技能：超级赛亚人（R 键，需复苏 10 级）",
        "",
        "鬼域：是",
        "",
        "§6成神：变身期间灵异伤害 ×2.5，移速 +30%"
));

GhostUtils.registerAddonGhostMapping("kakarot_ghost", new ItemStack(KAKAROT_GHOST_ITEM));
GhostUtils.registerAddonEntityCreationMapping("kakarot_ghost", KAKAROT_GHOST);
```

面板内容格式跟本体一致：`代号 / 被动 / 袭击 / 一级~十级 / 鬼域 / §6成神`，
列表按索引**交替分两列**，所以用空字符串 `""` 当留白占位。

> 另一个细节：`BaseGhostEyeItem#use` 往 ghostData 里塞的是 `"Name"`，
> 但 `GhostAbilityPopupS2CPacket` 读的是 `"CustomName"`（序列化 Text）。
> 两者对不上，所以弹窗标题实际走的是 `getGhostDisplayName(ghostType)` 这条路径 ——
> **只要注册了显示名映射，标题就正确了**，不需要改本体。
