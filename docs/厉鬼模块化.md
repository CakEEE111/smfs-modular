# 厉鬼模块化 · 开发文档

> 把 QisPlan2 的「厉鬼模块化」抽象，以**附属模组**方式接到神秘复苏 1.5.0 上。
> 不修改本体源码，不产生需要同步维护的分支。
>
> 本文是给「要往里加东西的人」看的。想先了解为什么这么做，直接跳到第 10 节。

---

## 0. 五分钟上手

一个能跑的最小模块：

```java
public final class MyModule implements GhostOnlyModule {

    public static final Identifier ID = new Identifier("smfsaddon", "my_module");

    @Override
    public Identifier id() { return ID; }

    @Override
    public List<GhostRule> rules() { return List.of(new MyRule()); }
}
```

注册（`onInitialize` 里）：

```java
GhostModuleRegistry.register(new MyModule());
```

挂到鬼上：

```java
GhostModules.attach(ghostEntity, MyModule.ID);
```

三行就完了。剩下的都是可选项。

## 1. 概念模型

六个东西，关系是单向的：

| 概念 | 谁持有 | 职责 |
|---|---|---|
| **宿主** `LingyiHost` | 鬼 / 方块 / 物品 / 玩家 | 提供能力、持有模块集合、存档 |
| **能力** `HostCapability` | 宿主实现 | 「我能做什么」，决定谁能装上 |
| **模块** `GhostModule` | 注册表（单例） | 声明：需要什么能力、有哪些规则和能力 |
| **模块数据** `GhostModuleData` | 宿主 | 每只宿主各自的强度 / 复苏值 / 自定义 NBT |
| **规则** `GhostRule` | 模块定义 | 判断何时触发、触发时做什么 |
| **事件** `GhostEvent` | 调度器产生 | 语义事件，规则按它筛选 |

一次执行的链路：

```
宿主.tick ──▶ Dispatcher.tick
                 │
                 ├─ 能力不满足 → 跳过
                 ├─ 推进自然复苏
                 ├─ 派发 GhostTickEvent
                 └─ 需要的话扫邻近玩家 → 派发 GhostNearbyPlayerEvent
                          │
                          ▼
                   Dispatcher.dispatch
                          │
                  元规则 → 优先级 → 互斥 → 执行 → 结算代价 → 记图鉴
```

**核心约束：模块实现必须无状态。** 所有可变数据放 `GhostModuleData`。
违反这条不会立刻报错，会在一百只鬼之后以「某只鬼的状态莫名共享」的形式炸出来。

## 3. 宿主与能力

### 能力清单

| 能力 | 方法 | 鬼实体 | 方块 | 物品 | 玩家 |
|---|---|---|---|---|---|
| `SpatialHost` | `world()` `position()` | ✔ | ✔ | ✔ | ✔ |
| `EntityHost` | `living()` | ✔ | ✘ | ✘ | ✔ |
| `GhostEntityHost` | `ghost()` | ✔ | ✘ | ✘ | ✘ |
| `TickHost` | `ticks()` | ✔ | ✔ | **需自己接** | ✔ |
| `PersistentHost` | `state()` `markDirty()` | — | ✔ | ✔ | ✔ |

鬼实体不实现 `PersistentHost`：它的模块数据由 mixin 统一写进实体 NBT，
插件用 `context.state()` 就够，不需要再多一个抽屉。

**物品和方块默认没有 tick**，这是最容易漏的一条。插件不能假设心跳免费。

### 模块声明需求

```java
public interface GhostOnlyModule extends GhostModule {
    @Override
    default Set<Class<? extends HostCapability>> requires() {
        return Set.of(GhostEntityHost.class);
    }
}
```

装载判据只有一条：`host.supportsCapabilities(module)`。不满足则
`attach()` 直接抛异常并报出缺哪个能力 —— **装载期炸掉，比运行时静默不生效好得多**。

三档预设，绝大多数模块挑一个就够：

| 预设 | 要求 | 能装到 |
|---|---|---|
| `SpatialModule` | `SpatialHost` | 鬼、道具、方块、玩家 |
| `LivingModule` | `EntityHost` | 鬼、玩家 |
| `GhostOnlyModule` | `GhostEntityHost` | 只有鬼 |

选择原则：**用能满足需求的最小能力**。顺手写 `GhostOnlyModule` 很方便，
但它会把这个模块永远锁死在鬼身上。

### 如何新增一种宿主

照抄 `block/GhostAnchorBlockEntity` 即可，清单是：

1. 实现 `LingyiHost`：`capability()` 用 `type.isInstance(this)`，`modules()` 返回容器；
2. 按需要实现能力接口 —— **只实现真正具备的**，不要图省事全实现；
3. 找个东西驱动 `GhostModuleDispatcher.tick(this)`：
   - 方块 → `BlockWithEntity#getTicker`
   - 物品 → 持有者 tick，注意背包遍历的成本
   - 玩家 → 已有的玩家 tick 通道；
4. 存档：`modules.writeNbt()` / `readNbt()` 塞进宿主自己的 NBT；
5. 如果想让它响应事件（受伤等），自己调 `GhostModuleDispatcher.damaged(...)`。

### 已有宿主对照

| | 鬼实体 | 方块（灵异锚点） | 物品（鬼灯笼） |
|---|---|---|---|
| 实现方式 | mixin 接口注入 | `BlockEntity` | 独立宿主对象 |
| 位置来源 | `getPos()` | 方块坐标 | 持有者位置 |
| 心跳来源 | `tick` 注入 | `getTicker` | `inventoryTick`（**降频 10 tick**） |
| 存档位置 | 实体 NBT `GhostModules` | 方块实体 NBT | 物品 NBT `SmfsAddonHost` |
| 能力 | Spatial / Entity / GhostEntity / Tick | Spatial / Tick / Persistent | Spatial / Tick / Persistent |

物品宿主是最尴尬的一种：它有位置、能存档，但**不是活物**，
所以不实现 `EntityHost`。一旦把持有者的能力算到物品头上，
「同一个插件挂上去行为一致」这个前提就破了。


### 为什么能力查询是零分配

`GhostEntity` 上的 mixin 直接把 `GhostEntityHost` / `TickHost` 注入目标类，
所以 `capability()` 就是一次 `isInstance` 加转型：不建包装对象、不查表。
这条路径每 tick 会走很多次，不能有分配。

## 4. 写模块

### 完整一点的样子

```java
public final class PressureModule implements SpatialModule {

    public static final Identifier ID = new Identifier("smfsaddon", "pressure");

    @Override public Identifier id() { return ID; }

    /** 每秒自然涨 0.5，0 表示不自然复苏 */
    @Override public double naturalRevivalRate() { return 0.5D; }

    /** 每 10 tick 扫一次 6 格内的玩家 */
    @Override public int nearbyScanInterval() { return 10; }
    @Override public double nearbyScanRadius() { return 6.0D; }

    @Override public List<GhostRule> rules() { return List.of(new Rule()); }
}
```

### 两种规则形态，同一个接口

**判定型**（被询问时表态）：

```java
private static final class Rule implements GhostRule {
    @Override public Identifier id() { return new Identifier("smfsaddon", "my/attack"); }
    @Override public boolean supports(Identifier eventId) { return GhostAttackRuleEvent.ID.equals(eventId); }

    @Override
    public boolean canTrigger(GhostModuleContext ctx, GhostEvent event) {
        GhostAttackRuleEvent e = (GhostAttackRuleEvent) event;
        // 用 entity() 而不是 ghost()：将来挂在玩家上也成立
        return e.player().getY() < ctx.entity().getY() - 1.0D;
    }

    @Override
    public void onTrigger(GhostModuleContext ctx, GhostEvent event) {
        ((GhostAttackRuleEvent) event).allow();
    }
}
```

**反应型**（事情发生时反应）：

```java
@Override public boolean supports(Identifier id) { return GhostNearbyPlayerEvent.ID.equals(id); }

@Override
public void onTrigger(GhostModuleContext ctx, GhostEvent event) {
    ctx.state().putInt("seen", ctx.state().getInt("seen") + 1);   // 随存档保存
}
```

### 看不见的时候

模块最麻烦的失败模式不是崩溃，而是**静默不工作**，或者反过来——
**其实工作了但外面看不出来**。后者的典型例子：给玩家上缓慢，
而测试时在创造模式飞行，缓慢对飞行无效，看起来就像完全没生效。

所以框架留了一个开关式观察口：

```java
GhostDebug.notice(player, "被压住了 " + (int) context.revival());
```

默认什么都不做，`/ghostmodules debug` 打开后才在动作栏显示。
调试可见性可以留在代码里，而不会污染正式玩法。

配套的还有 `/ghostmodules held`：把物品宿主的模块、复苏值、是否到阈值摊开印出来。



### 挂载方式

```java
// 1) 新鬼的构造器里
public MyGhost(EntityType<? extends GhostEntity> type, World world) {
    super(type, world, true, 1, 6.0D, 'B');
    GhostModules.attach(this, MyModule.ID);
}

// 2) 给本体已有的鬼补挂
ServerEntityEvents.ENTITY_LOAD.register((entity, world) -> {
    if (entity instanceof GhostEntity ghost && !GhostModules.has(ghost, MyModule.ID)) {
        GhostModules.attach(ghost, MyModule.ID);
    }
});

// 3) 非实体宿主
GhostModuleDispatcher.attach(myBlockEntity, MyModule.ID);
```

### 别人怎么用

```java
// 第三方附属的 onInitialize
GhostModuleRegistry.register(new TheirModule());
```

模块系统是公开 API，不需要改本体、也不需要改本模组。
**一个模块一个文件**，落地成本比写一整个鬼类低一个数量级。

## 5. 规则组合

| 方法 | 作用 | 默认 |
|---|---|---|
| `priority()` | 同时满足条件时谁先执行，大的先 | `0` |
| `exclusionGroup()` | 同组只允许一条触发 | `null` |
| `revivalGain()` | 触发一次的复苏代价 | `0` |
| `codex()` | 图鉴条目 | `null` |

调度顺序：

```
元规则一票否决 → 调参过滤 → 事件筛选 → 条件判定
      → priority 降序 → 同组去重 → 执行 → 结算代价 → 记图鉴
```

**互斥组**表达的是「规则互相制约」。`DomainPresenceModule` 里
「发狂」（8 格内，优先级 100）与「察觉」（12 格内，优先级 10）共用一组：
玩家站 5 格时两条都满足，但只有发狂生效。不是叠加，是一条压倒另一条。

### 元规则

有些规则不属于「满足条件就触发」，而是**无视其他一切规则**（必死诅咒）：

```java
public interface GhostMetaRule {
    Identifier id();
    boolean vetoes(GhostModuleContext context, GhostEvent event);
}
```

在 `metaRules()` 中声明。任一返回 `true`，本模块的普通规则全部跳过。

### 协同：拼上之后多出来的东西

互斥是「两块拼不上」，协同是「两块拼上会多出什么」。只有负向约束的话，
模块化最多叫插件化 —— 玩家永远感受不到「这只鬼被拼完整了」的那个瞬间。

协同本身就是一种模块，不新造任何调度机制：

```java
GhostCombo.of(new Identifier("smfsaddon", "cornered"))
        .needs(StepGhostModule.ID, DomainPresenceModule.ID)   // 同时具备这两个模块
        .needsCapability(GhostEntityHost.class)
        .rules(new CorneredRule())                            // 解锁的新规则
        .build();
```

由调度器根据宿主的模块集合自动挂载 / 卸载：

```
宿主同时具备所需模块 → 自动 attach 协同模块
所需模块缺失        → 自动 detach
```

于是优先级、互斥组、元规则、复苏代价、图鉴记录**全部原样复用**，
不会出现「协同规则和普通规则行为不一致」的裂缝。

内置示例「墙角必杀」：踩人鬼 + 鬼域压迫 → 贴脸 3 格内无视高度差。
原本站高处就安全，拼上之后站哪儿都没用 —— 不是数值变大，是一条新规律出现了。

成本：协同数量是个位到十位级，每 tick 只有几次 map 查找。

## 6. 代价与调参

框架只负责结算，含义留给内容：

- `revivalGain()` 触发即累加；`naturalRevivalRate()` 每秒自然增长；
- `context.revived()` 只回答「是否顶到上限」，不规定后果；
- 内容可以据此让规则变强、让鬼失控，或者什么都不做。

全局调参，改一次所有用到该规则的宿主同时生效：

```java
GhostRuleTuning.setRevivalScale(ruleId, 0.5D);   // 代价减半
GhostRuleTuning.setEnabled(ruleId, false);       // 停用
GhostRuleTuning.reset();
```

## 7. 图鉴

模块化真正的回报：**规则变成可索引的数据，才能被记录、被逐步揭示。**

```java
@Override
public GhostCodexEntry codex() {
    return GhostCodexEntry.of("低处踩踏", "只袭击比自己低至少一格、且在 28 格内的目标");
}
```

`GhostCodexEntry(title, hint, hintRevealAt)` 按观察次数逐步解锁。

**记录时机**：规则真的执行完之后，且同时满足 —— 规则声明了 `codex()`、
事件带玩家、宿主是鬼实体。没有旁观者的规律不进图鉴。

**存储**：本体玩家数据里，键 `smfsaddon_codex`，格式
`{"smfs:step_ghost|smfsaddon:step_ghost/low_ground": 3}`，另存版本号
`smfsaddon_codex_v`。跟随原版存档，不需额外文件。

## 8. 接入本体

### 注入点（`GhostEntityModuleMixin`）

| 注入 | 目标 | 作用 |
|---|---|---|
| `@Inject` HEAD | `tick` | 每 tick 调度，仅服务端 |
| `@Inject` TAIL | `writeCustomDataToNbt` | 模块数据随实体存档 |
| `@Inject` TAIL | `readCustomDataFromNbt` | 读档还原 |
| `@Inject` HEAD | `damage` | 派发受伤事件 |
| `@Redirect` | `tick` 内对 `shouldAttackPlayer` 的调用 | 杀人规律三态裁决 |

为什么重定向「调用点」而不是注入 `shouldAttackPlayer` 本身：
**35 个子类覆写了它**，注入基类捕获不到覆写者。

已核对的映射（1.5.0）：

```
tick                 → method_5773()V
writeCustomDataToNbt → method_5652(Lnet/minecraft/class_2487;)V
readCustomDataFromNbt→ method_5749(Lnet/minecraft/class_2487;)V
damage               → method_5643(Lnet/minecraft/class_1282;F)Z
```

本体升级后只需重新核对这四行，框架代码不用动。

### 入口顺序不是确定的

`depends` **不保证** `main` 入口按依赖顺序执行。实测同一次构建的两次启动，
一次 `smfs` 先、一次 `smfsaddon` 先。抢在前面时 `GhostAPI.isRegistered()` 为 `false`，
内容注册被跳过，掉落表 / 成就全部报 `unknown string 'smfsaddon:...'` ——
看着像数据文件写错，其实是注册没发生。

解法：不赌顺序，把「本体初始化完了」变成确定性事件。

```
SmfsAddon.onInitialize()
    ├─ 本体已就绪 → 直接注册
    └─ 未就绪 → pendingContentRegistration = true
                      ↓
SmfsInitializerMixin @Inject(Smfs#onInitialize, TAIL)
    └─ SmfsAddon.onSmfsReady() → 补注册
```

细节：混入本体的 `onInitialize` 必须 `remap = false`，否则注解处理器报
`Unable to locate obfuscation mapping`；也不能用 `ServerLifecycleEvents` 延后，
那时注册表已冻结。

## 9. 已知限制与路线图

**限制**

- `@Redirect` 用了 `require = 0`：本体改掉那个调用点会让裁决静默失效，
  其余功能（tick、存档、受伤）不受影响。升级后对照第 8 节核对。
- 模块状态只在服务端，不同步到客户端。
- **方块 / 物品宿主上的模块不进图鉴**：`RuleCodex` 需要「鬼类型」，
  非实体宿主没有。补齐需要引入 `LingyiHost.hostId()`，是结构性改动。
- `useAbility` 只是 API，没有键位和网络包。

**路线图**（按优先级）

1. **图鉴 GUI** —— 数据层已就绪，只剩渲染。
2. **变体条件** —— 现在只有权重随机，还不能「鬼域 ≥2 才用那套」。
3. **图鉴支持非实体宿主** —— 需要 `LingyiHost.hostId()`。
4. **迁移本体更多鬼** —— 现在只有 6 个内置模块，其余靠本源规律兜底。

## 10. 与 QisPlan2 的边界

只借用抽象结构，不复制实现代码。原因有二：
QisPlan2 的 `gradle.properties` 标注 `All Rights Reserved`（README 写 MIT，两者矛盾），
且其实现深绑 NeoForge 数据附件与 1.21 API，直接搬过来反而要重写。

本实现按 Fabric 1.20.1 / Yarn 命名、围绕 `GhostEntity` 重新设计，
与本体 `GhostUtils`、`GhostAPI` 的既有扩展点互补而非替代。

QisPlan2 的三处原设计与本实现的差异：

| QisPlan2 | 本实现 | 原因 |
|---|---|---|
| 模块挂数据附件，可挂方块/物品/实体 | 宿主按能力声明 | Fabric 1.20.1 无 Attachment API |
| 一只宿主通常一个模块 | 一只鬼 = 一组模块 | 本体 43 只鬼是「一个类一种行为」，需要组合 |
| 规则直接决定攻击与否 | 三态表决 | 必须与 35 个覆写了 `shouldAttackPlayer` 的子类共存 |

## 11. 为什么不做玩家宿主

一个曾经考虑过、**已经决定放弃**的方向：把模块挂到玩家身上，让「技能」变成一种宿主形态。

放弃的理由不是技术难，而是**归错了家**。

### 本体已经有一套驭鬼者体系

`GhostSkillManager` 里是一堆按鬼种写死的方法：

```java
public static void handleGhostFistActiveSkill(PlayerEntity player, LivingEntity target)
public static void handleGhostFistPassiveSkill(PlayerEntity player, LivingEntity target)
...
if ("ghost_fist".equals(ghostType)) { ... }
```

也就是说，「玩家驾驭某只鬼之后能干什么」这件事，本体已经管了，
而且是在技能分发逻辑里直接判鬼种字符串。

再叠一层玩家宿主会变成：同一只鬼，作为敌人有一套规律（我们的模块），
作为被驾驭者另有一套技能（本体写死）。**两套东西讲同一件事，却互不知情。**

### 关键事实：被驾驭的鬼不在场上

鬼槽里存的是数据，不是活体实体：

```
GhostSlots → { 物品栈, ghostType 字符串, 等级, 复苏度 }
```

没有实体，就没有 `GhostModuleContainer`，也就**没有模块可以「借」给玩家**。

所以「技能 = 借用所驾驭之鬼的模块能力」这个想法，在当前的鬼槽结构下不成立。
要成立，必须先有装配表：让「鬼类型」本身拥有一份模块清单，
与场上有没有活体实例无关。

### 于是装配表从「锦上添花」变成「硬前置」

```
                    ┌── 活体鬼：按装配表挂模块 → 规律生效（敌人侧）
鬼类型 ──装配表──┤
                    └── 鬼槽里的同类型鬼：查同一份清单 → 技能候选（玩家侧）
```

有了这张表，两侧才共享同一份定义；没有它，两侧永远是两套互不相干的东西。

而装配表本身即使不为了技能也该做：现在每只鬼都要在构造器里手写挂哪些模块，
加一只鬼要改 Java 并重新编译 —— 这和「插件化」是矛盾的。

### 结论

- 玩家不作为宿主；
- 玩家侧交给本体驭鬼者体系，不重复造；
- 我们先做装配表，把「鬼类型 → 模块」变成数据；
- 之后如果要让技能也走模块，接入点是本体的技能分发，那是另一个课题，
  代价是需要 mixin `GhostSkillManager` 的多个方法，耦合很深，暂不做。


## 12. 装配表：自动适配任何附属的鬼

装配表的键是**实体类型 ID**，不是 Java 类。这是「自动适配别人的鬼」的全部秘密 ——
只要那只鬼继承本体 `GhostEntity`（也就带着模块容器），就会按表装配，
**对方一行代码都不用改**。

### 数据包格式

`data/<任意命名空间>/ghost_assembly/*.json`：

```json
{
  "entity": "smfs:qiaomen_ghost",
  "variants": [
    {
      "id": "只敲门",
      "weight": 4,
      "modules": ["smfsaddon:step_ghost"]
    },
    {
      "id": "拼完整",
      "weight": 1,
      "modules": ["smfsaddon:step_ghost", "smfsaddon:domain_presence"]
    }
  ]
}
```

也兼容单变体写法（整个文件就是一套）：

```json
{ "entity": "smfs:qiaomen_ghost", "modules": ["smfsaddon:step_ghost"] }
```

`id` 只用于日志与调试，不参与逻辑；`weight` 至少为 1。

文件夹命名空间不参与解析：第三方可以在自己的数据包里写，
整合包作者可以统一覆盖，玩家也能自己塞一个。

### 变体：灵异拼图的随机性

同一只鬼可以有多套拼法，生成时按权重抽一个。

**抽中即固定**：变体索引写进实体 NBT（`SmfsAddonVariant`），读档后沿用。
这一条是必须的 —— 如果每 tick 重抽，鬼的规律会闪烁，
玩家没法推理，图鉴也就失去意义。

数据包改动导致变体数量变少时，旧索引会越界，此时退回重新抽一个。
这个退化是刻意留的：宁可让老存档的鬼换一套规律，也不能让它变成空壳。

### 装配规则

| 规则 | 说明 |
|---|---|
| 装配时机 | 实体首次 tick（仅服务端） |
| 变体选择 | 有 NBT 索引就用索引，否则按权重抽 |
| 装配范围 | **只补缺失的模块** |
| 装配次数 | 每只鬼一次（运行时标记，不落盘） |
| 失败处理 | 模块未注册 / 能力不匹配 → 警告并跳过，不影响其它模块 |

「只补缺失 + 每只鬼一次」这两条合起来的效果是：
手动挂上的不会被覆盖，手动卸掉的也不会每 tick 被加回来。

### 刷新

服务端数据包重载（进世界、`/reload`）时刷新装配表。
已经生成的鬼不会重组 —— 装配发生在实体首次 tick，已经在跑的实例只认当时那份表。

### 查看

```
/ghostmodules assembly        列出当前载入的装配表
```

### 为什么这是「插件化」的关键一步

在这之前，加一只鬼要在构造器里手写挂哪些模块 —— 加鬼等于改 Java 重新编译。
有了装配表，「这只鬼由哪些规律组成」变成了数据：

```
鬼类型 ──装配表──▶ 模块组合
```

它同时解决了第 11 节里的那个矛盾：同类型鬼作为敌人和作为被驾驭者，
从此可以查同一份清单。

## 13. 灵异装置：把厉鬼当插件装进装置

主界面（`GhostControlScreen`）右侧多了一个「装置」按钮，点开是一个两槽界面：

- **左槽**：目标物品（剑、木棍、任何东西）
- **右槽**：厉鬼容器（鬼眼之类）
- 点「合入」把这只鬼的规律**移植进左侧物品**

合入成功后，这件物品就带着鬼的规律了 —— 用它对门挥一下，
门后一片尽灭（`door_bane`）。剑还是剑，只是开了门会死人。

### 入口是怎么加的

本体的子入口不是标准按钮控件，而是「render 里手绘 25×25 方块 + mouseClicked 里判区域」。
所以 `GhostControlScreenMixin` 照抄同样做法，挂两个点：

```
@Inject render TAIL        → 画按钮（位置 x+200, y+183）
@Inject mouseClicked HEAD  → 命中则发空包给服务端，取消原方法
```

本体已占用 +8 / +43 / +78 / +113 / +148，间隔 35，+183 是下一个空位。
**这是写死的坐标** —— 本体将来再加一个入口就会撞上，届时改常量即可。

细节：mixin 继承 `HandledScreen` 而不是用 `@Shadow`。`x` / `y` / `textRenderer`
是继承来的 protected 字段，`@Shadow` 解析不到目标，控制台会给
`Cannot find target for @Shadow field` 的警告并在运行时失败。

### 公式

两侧各算一个数：

```
压制值 = 灵力上限 × 0.10 + 灵异抗性 × 1.00 + 灵异伤害 × 0.50

需求值 = Σ(模块 suppressionCost) × COST_SCALE × (1 + 0.75 × 物品上已有的鬼数)
```

两个系数都在 `FusionFormula` 里：

| 常量 | 作用 |
|---|---|
| `ENTRY_COST`（当前 150） | 每次合入的入门费，与融几个模块无关。没有它，第一只鬼只要 900，而压制值动辄上万——等于没有要求 |
| `COST_SCALE`（当前 30） | 整体成本倍率。模块的 `suppressionCost()` 只是「相对危险度」，乘上它才是实际要压的量级 |
| `MARGINAL_GROWTH`（当前 0.75） | 边际成本。同一件物品每多融一只鬼，成本上浮 75% |

边际成本是为了堵住「一把剑塞十只鬼」——不只是数值问题，
融合太多本来就会让技能面板失控。

按当前参数，只有本源规律的鬼从第一只起分别是
**5400 / 9450 / 13500 / 17550 / 21600**（压制 12517 的话，前两只是稳的，
第三只起开始赌：胜率约 77% → 46% → 30%）。要整体加减负只改 `ENTRY_COST`。

**界面与实际必须同一套口径。** 早先 `recompute` 用的是 `modulesOfGhost`（只含装配表模块），
而 `performGraft` 用的是 `graftPlanFor`（装配表 + 本源规律）——
没有装配表的鬼在界面上算出来是 0，显示「无需求」，实际却照样收 900。
现在两边都走 `graftPlanFor`。

压制足够时**必定移植、不受反噬**；压制不足时不是直接失败，而是**赌一把**：

```
成功率 = (压制 / 需求)² × 0.9，限制在 5% ~ 75%

赌赢 → 规律仍然进去，但反噬 ×0.6（硬吃下来的代价）
赌输 → 规律进不去，反噬 ×1.2
```

平方是为了让「差一点」有意义但不廉价：压制到需求的 90% 时约 73%，
掉到 50% 就只剩 22%。无论输赢都要付反噬 —— 这才是「压不住硬来」该有的代价。

三个权重写在 `FusionFormula` 里，是整套玩法的平衡旋钮；
`suppressionCost()` 是 `GhostModule` 的新方法，默认 30，按规律危险程度上调。

界面把两个值都显示出来，玩家能自己算还差多少，而不是靠试。

### 反噬

**只在合入时结算一次**，不是持续掉血。三项同时作用：

| 项 | 范围 | 方式 |
|---|---|---|
| 理智 | −4 ~ −24 | `addSpiritAttribute(SANITY, -x)` |
| 生命 | −2 ~ −12 | 魔法伤害，可能致死 |
| 复苏度 | +1 ~ +5 | 所有已占用鬼槽 |

强度看**缺口占比** `(需求 − 压制) / 需求`，再乘倍率（赌赢 0.6 / 赌输 1.2）：

```
缺口 10% → 理智 −6    缺口 34% → 理智 −12    缺口 80% → 理智 −20
```

### 为什么按比例而不是按差值

最早写的是「差值 × 系数再截断」。融合成本放大之后，差值动辄上千，
乘出来全部撞上限——**每次失败都是同样的满额惩罚**，
「差一点」和「差一倍」没有区别，缩放彻底失效。

改成比例后与数值量级无关，本体再调整灵异属性的量级也不会重演这个问题。

复苏度那一项绕了一下：1.5.0 没有单槽位写入接口，只有
`decreaseAllSlotRevivalDegree`。它对每槽做 `max(0, current - amount)`，
所以**传负数就是增加**。走本体自己的写入路径（会同步、会存档），
比直接改 NBT 安全。

### 合入时发生了什么

点「合入」不是「把鬼复制一份」，而是按两条来源挂模块：

| 来源 | 覆盖什么 | 需要为每只鬼写代码吗 |
|---|---|---|
| **本源规律** | 任何鬼的杀人判定（`shouldAttackPlayer`） | 不需要 |
| **装配表模块** | 鬼域、开门这类写在 `tick` 里的行为 | 需要，但按机制算 |

成功后**消耗右槽的厉鬼**——规律已经进了物品，鬼还留着就能无限复制。

物品上的词条只显示**里面是哪几只鬼**，不显示模块名：模块是实现细节，
而且一条规律可能由多只鬼提供，按模块列会撒谎。

一次合入会往同一个 `native_rule` 实例里追加绑定，所以**可以多次合入不同鬼**，
`Custom.GhostTypes` 用逗号分隔。早先只存单值，融第二只就把第一只覆盖了。

### 已知限制

- 数值没平衡过，权重和代价都是第一版估值，界面能看到实际数字。
- 反噬只对持有装置的人生效，没有惩罚"把装置丢给别人"。
- 界面是纯色块画的，没有贴图 —— 也因此在任何资源包下都不会缺图。

## 14. 本源规律：直接调用鬼自己的判定

前 13 节都在做一件事：把规律拆成模块。但那有个根本弱点 ——
**每只鬼都要写一次适配**，换一只附属鬼就得再写一遍，那不叫插件化。

破局点在一条统一入口：本体的鬼虽然把规律写死在类里，却**统一覆写了**
`GhostEntity#shouldAttackPlayer(PlayerEntity)`。于是做法从「复制逻辑」变成「调用逻辑」：

```java
GhostEntity shadow = type.create(world);            // 造一个不进世界的实例
shadow.setPosition(攻击者的坐标);                     // 摆到施法处，让坐标判定成立
if (shadow.shouldAttackPlayer(目标)) {               // 鬼自己的逻辑，原样执行
    目标.damage(ModDamageSources.ghost(world), 1000);
}
shadow.discard();
```

不复制任何判定——`StepGhostEntity` 是它自己的高度比较，`QiaomenGhostEntity`
是它自己的条件，我们一概不需要知道。

### 边界在哪

主模组把一只鬼的能力**散在好几处**，只有一处是统一的：

| 能力类型 | 本体入口 | 能否零适配 |
|---|---|---|
| 杀人规律 | `shouldAttackPlayer` | ✅ |
| 替死 | `ScapegoatGhostItem.handleScapegoatPassiveSkill` | ❌ 要一次模块 |
| 鬼域 / 开门 | 写在 `tick` 里 | ❌ 要一次模块 |
| 主动技能 | 见第 15 节 | ✅（靠混入） |

所以「全部零适配」做不到，能守住的底线是：**每一处都直接调本体，不复制判定**。
这样本体改了规则，附属跟着变，不会分叉。

### 影子实例的两个坑

- `type.create()` 对**只有物品、没有实体**的鬼（替死鬼、许愿鬼）返回 null ——
  这类鬼只能靠模块，不能靠本源规律。
- 影子不进世界，依赖世界状态的判定（「附近还有几只鬼」之类）结果会和真实情况有偏差。

## 15. 技能：从通道推导 + 一个混入

「把鬼合进物品之后能放它的技能」这件事，前后走过三条路：

1. 手写 17 条技能表 —— 漏一大半
2. 反射扫 `handleXxxSkill` 方法名 —— 能收 31 鬼种 / 45 技能，但**本体自己命名不统一**，
   实测融了 5 只鬼，面板一行技能都没有
3. 扫**技能通道**（现在的做法）—— 通道就是全集，且对附属同样成立

### 为什么反射不够

反编译 1.5.0 之后看清了：

| 鬼 | 实际情况 |
|---|---|
| 鬼血 | 没有 `handleGhostBloodSkill`，逻辑直接写在 `ClientGhostBloodSkillC2SPacket` 里 |
| 鬼湖 | 同上，包里内联操作鬼仆实体 |
| 静悄悄 | 调的是 `SilentGhostTeleportHandler.handleJKeyTeleport`，名字完全不符合约定 |
| 完整鬼影 | 用 `ghost_shadow_head_*` 那四个包，包内判定写「完整鬼影 **或** 鬼影头」 |
| 鬼眼 | 包叫 `ghost_eye_j_skill`，但判定认 `silent_ghost_eye` |
| 鬼烟 | 物品鬼种 `ghost_smoke`，包是 `ghost_wind_skill`（那是另一只鬼风）——它确实没有主动技能 |

也就是说，「方法名 → 鬼种」这个映射在本体内部就不可靠，词表做得再细也会错配
（早先 `handleShadowGhostJSkill` 被最长匹配成了 `complete_shadow_ghost`，实际是影子鬼的）。

### 现在的做法

`GhostSkillChannels` 扫 `ClientPlayNetworking.getSendable()`：

```
<鬼种>_skill            → 默认技能
<鬼种>_<n|g|v|j>_skill  → 对应按键
client_<鬼种>_<键>_skill → 去掉 client_ 前缀
```

通道名本身的语义是本体定的，客户端能发的东西就是技能全集 —— 顺带把
**附属自己的技能**也收了进来，不需要认识它们的类。

只有两处通道名与鬼种名对不上（完整鬼影、鬼眼），写成一张两行的
`CHANNEL_ALIAS`，每行都有反编译依据，不是猜的。

### 一个混入打通全部资格判定

这些技能内部都靠 `PlayerEvents.hasGhostType(player, ghostType)` 确认
「你有没有这只鬼」。所以只改这一个方法：

```java
@Inject(method = "hasGhostType", at = @At("RETURN"), cancellable = true, remap = false)
// 背包里带着融合了这只鬼的物品 → 也算拥有
```

**不需要逐个技能适配**，它们自己的资格检查就通过了。

### 面板

`X` 键打开，**只列当前手持那件物品上的鬼**（主手优先，其次副手）。
背包里同时放几把融合武器时，各看各的，不会混成一锅 —— 面板标题下面会标出
"这块面板属于哪件装备"。手里没有融合物时按 X 只给一句提示，不开空界面。

注意这里和资格口径的差别：技能资格按「背包携带」判定（见第 17 节），
但面板只认手持。这不矛盾——资格回答"能不能用"，面板回答"这件装备有什么"。
想用背包里另一把武器的技能，拿起来按 X 就行。

条目按屏幕高度动态分页——一只鬼最多四个键位，合几只就会超出屏幕。
没有主动技能的鬼（比如鬼烟）也占一行，写「（无主动技能）」，避免玩家以为没合上。

### 面板的边界：只收 `_skill`

本体 1.5.0 一共 137 个 C2S 通道，其中 67 条以 `_skill` 结尾。面板收的就是这批
（再排除 3 条要读参数的），其余 70 条**故意不碰**：

| 类别 | 例子 | 为什么不收 |
|---|---|---|
| 鬼域能力 | `ghost_domain_toggle`、`ghostdomain_pause_time`、`ghostdomain_teleport` | 不是"以鬼为单位"的技能，本体有自己的开关/界面 |
| 次级操作 | `lost_ghost_restart`、`ghost_officer_restart`、`consume_shard` | 跟着各自流程走，单独触发没有意义 |
| 系统/UI | `open_*`、结构坐标请求、鬼童融合 | 不是技能 |

**另有 3 条 `_skill` 也不能收**：`ghost_shadow_head_g/n/v_skill` 要读
`readInt` / `readFloat` / `readBoolean`（目标实体、坐标）。面板发的是空包，
会让服务端 handler 读越界——轻则日志报错，重则踢人。所以列在 `NEEDS_ARGUMENTS` 里排除。
完整鬼影经别名正好落到这三个包，也被挡掉。

逐个反编译确认过：67 条里只有这三个读参数，其余都是无参的。

### 自己模组的技能：自己登记

卡卡罗特的变身 / 龟派气功走的是 `smfsaddon:kakarot_transform` / `kakarot_kamehameha`
—— 历史命名，键位 R / C 直接发这两个包，从名字上看不出是技能，按后缀扫不到。
所以最初融了卡卡罗特，面板显示「无主动技能」。

`GhostSkillChannels.registerExtra(鬼种, 按键, 通道, 显示名)` 解决这一类：
谁注册谁负责，不改协议名，也不往解析器里塞特例。

### 冷却：把包打回去，而不是抄参数

第一版想的是照抄本体的冷却参数（每个技能用哪个键、多少刻）。这是反过来的：
本体每加一个技能就得补一行，表一旦对不上就静默失效——正是最差的泛化。

现在改成**面板直接发本体自己的技能包**。本体的每个技能包都是这个结构：

```
if (!checkAndSetJSkillCooldown(player, 键, 刻数, 技能名)) return;   // 冷却 + 异类 0.75 倍率
if (canUseGhostSkill(...) == NO_GHOST) return;                     // 资格
handleXxxSkill(player);                                            // 行为
PlayerEvents.balanceRevivalDegree(player);                         // 收尾
```

我们只做两件事：

1. **`GhostSkillChannels` 给出通道**：从 `getSendable()` 里按 `_skill` 后缀推出来
   （见上一节），点按钮时把这些通道原样发出去。
2. **`GhostDomainManagerSkillMixin` 放行资格**：在 `canUseGhostSkill` 的 HEAD，
   融合物品持有者直接返回 `SUCCESS`。没有这一步，本体会因为主鬼槽是空的
   而判 `NO_GHOST`，表现是「点了技能，弹一句『你还没有驾驭X鬼』」。

于是冷却、倍率、冷却提示文案、复苏平衡全部是本体那份，一行数值都没抄。
本体以后加技能，只要沿用「发自己的包」这个约定，我们零改动。

回退路径（本体没开通道的技能）仍走反射，但服务端会先调一次本体的
`checkAndSetJSkillCooldown`（共享 J 键 20 刻），所以没有「可以连点」的口子。

代价要说清楚：`canUseGhostSkill` 里的等级检查被一并跳过了。
融合物品没有本体那套等级体系，这是有意的口径——
手上拿着融合了某只鬼的物品，就当作驾驭了它，与 `hasGhostType` 那条保持一致。

### 复苏代价记在谁头上

分成两套，各按各的规则走，**不要互相套用**：

| 技能来源 | 结算函数 | 代价落在哪 |
|---|---|---|
| 本体技能（面板转发的 `_skill` 包） | 包里自带的 `PlayerEvents.balanceRevivalDegree` | **主鬼 +20、其他槽 −8**（本体原样） |
| 卡卡罗特变身 / 龟派气功 | `KakarotSlots.chargeRelease` | 卡卡罗特**自己**：在槽里加那一格，只有物品就加物品上那条规律，+12 |

为什么不一样：本体技能是以「主鬼」为代价设计的（技能挂在主鬼身上），
而卡卡罗特那两个技能挂在**物品**上，代价必须跟着物品走。

曾经把变身也接到 `balanceRevivalDegree` 上，结果是：玩家只把卡卡罗特融在武器里时，
放一次变身，主鬼槽里那只**毫不相干的鬼**复苏度 +20 —— 已修（`KakarotSlots`）。
面板转发本体技能时仍会+主鬼的复苏度，这是本体语义，保留。

## 16. 物品侧的事件总线

规律要活在物品上，就需要「玩家拿着它做了什么」这几类事件：

| 事件 | 触发点 | 用途 |
|---|---|---|
| `GhostItemUseEvent` | `ServerPlayerInteractionManager#interactBlock`（对块）、`ItemStack#use`（对空） | 开门必死这类 |
| `GhostAttackHitEvent` | `ItemStack#postHit` | 打在目标身上的规律 |
| `GhostOwnerDamagedEvent` | `PlayerEntity#damage` HEAD | 替死这类护主 |

### 为什么对块要从 `interactBlock` 拿

一开始挂在 `ItemStack#useOnBlock` 上，实测**右键门根本不触发**——
门属于「方块自己处理交互」的一类，物品那条分支被跳过了。
`interactBlock` 是所有分支的上游，一定被调用。对空气则走 `use`，两者不重叠。

### 护主那条要防递归

替死逻辑内部可能再次造成伤害，`ownerDamaged` 里加了重入标记，
否则会无限套娃。

### 替死的等级从哪来

本体 `getScapegoatGhostLevel` 只查**鬼槽**里替死鬼那一格的 `level`。
融合在盾牌上的替死鬼没有槽位，永远返回 1 级 —— 理智、灵异只回 20%，
跟玩家养了多久毫无关系。

`ScapegoatLevelMixin` 在方法 RETURN 处改写：拿融合物品时取
**所有已占用鬼槽里最高的 `level`**（等级在本体里随复苏度跨档改写，
所以「最高复苏等级」就是 `level` 的最大值），一个都没有才回落到 1 级。

只在 `FusedGhostIndex.holds(player, "scapegoat_ghost")` 时生效，
鬼槽用户的原有行为一个字不改。

注意：`getGhostDomainRadius` 是另一条独立扫描（找不到替死鬼槽位就返回 15），
不跟这个等级联动。也就是说融合物品的替死范围恒为 15 格，只有回复量随等级走。

### 物品的灵异伤害：每只鬼窃取 10%

融合物品打人时，除了原版伤害，还会额外造成一份**灵异伤害**：

```
灵异伤害 = Σ (每只融进去的鬼，其驾驭物灵异数值 × 10%)
```

**数值从哪来**：不另建表，直接读本体给这只鬼注册的驾驭物
（`smfs:<鬼种>`，`BaseGhostEyeItem`）上的 `getSpiritDamageBonus()`。
好处是改平衡只改本体一处，附属的鬼只要按本体方式注册驾驭物就自动有数。
找不到驾驭物的（只有实体、没有物品的鬼）按 0 算，不猜。

**为什么必须走 `ModDamageSources.ghost()`**：原版 `playerAttack` 打在鬼身上
会被当成无效伤害——有数字飘出来，实际不掉灵异强度。本体那条通道才是"灵异伤害"。

**一个必须处理的细节**：这段代码跑在 `ItemStack.postHit`（普通攻击之后），
目标还处在 10 tick 无敌帧里，直接打会被吞掉。所以要先 `timeUntilRegen = 0`
再施加——灵异伤害是**叠加**在原版伤害上的，不是替换。

改比例只改 `GhostSpiritPower.STEAL_RATIO`。按本体驾驭物的数值（12~15 一类），
一只鬼约 +1.2~1.5，融五只 ≈ +6~8。

## 17. 让附属看见融合的鬼：虚拟鬼槽

### 三条识别路径，我们只堵住了一条

附属判断「玩家有没有某只鬼」，实际有三条路：

| 路径 | 例子 | 我们有没有覆盖 |
|---|---|---|
| `PlayerEvents.hasGhostType(player, 鬼种)` | 本体自己的技能判定、血湖技能、鬼手腐蚀免疫 | ✅ 一个混入放行（按「背包携带」算） |
| `TameableItemAPI.isGhostSlotOccupied` + `getGhostTypeInSlot` 扫 0~9 槽 | 鬼域不定（梦游鬼、血湖等） | ✅ 虚拟鬼槽投影 |
| `PlayerEvents.getGhostSlotItem` 直读 | 饿死鬼、鬼手被动、鬼画 | ❌ 没覆盖（动了会伤本体存档逻辑） |

实测踩的就是第二条：把「梦游鬼」融进物品后，夜里不失控。
翻它的字节码，`DreamWalkerPassiveHandler` 里循环 10 次问 API 要槽位，
完全没走 `hasGhostType` —— 所以前面那个混入再对也没用。

### 拥有 ≠ 手持

`hasGhostType` 问的是「你有没有驾驭这只鬼」，不是「你现在拿没拿着」。
鬼槽里的鬼不会因为切物品就消失，融合物品也不该——所以那条混入按
**背包携带**判（`FusedGhostIndex.carried`），连着护甲和副手一起扫。

但「用剑开门」「打中目标触发规律」仍然只认手持（`FusedGhostIndex.holds`），
那是使用行为，不是拥有关系。两条口径分工写在 `FusedGhostIndex` 的注释里。

### 做法：往空闲槽位投影

`FusedGhostSlots` 把玩家背包里所有融合鬼按顺序去重，然后占用
**空闲的真实槽位**（第 k 只融合鬼 → 第 k 个空槽），`TameableItemAPISlotsMixin`
在 `TameableItemAPIImpl` 上把这些槽位报成「有鬼、鬼种是 X」。

于是附属扫槽时看到的是自洽的一组槽位：问占用得 true，问鬼种得对的类型。
**一处改动覆盖所有按 API 扫槽的附属**，不需要认识它们，也不需要为某只鬼写适配。

### 为什么只碰读取

投影槽在 `PlayerEvents` 里是空的。附属若对这些槽写复苏度/等级，
会往一个不存在的槽里塞数据，把存档搞脏 —— 所以 setter 与 `clearGhostSlot`
在投影槽上一律取消。融合物品的强度应该由物品自身（模块、复苏度）决定。

### 为什么不动 `hasTamedGhost`

本体自己也用 API，但只用到两个方法：`hasTamedGhost`（`BaseGhostEyeItem` 绑定新鬼时判重、
`GhostPianoBlock`）和 `getGhostType(stack)`。这两个<b>一行没改</b>，
所以「把鬼绑进鬼槽」这条主流程跟原来完全一样。

### 怎么排查

```
/ghostmodules slots
```

按 API 视角列出所有占用槽位，并标出哪些是「融合物品投影」。
附属的被动不触发时，先跑这条：如果投影没出现，问题在投影；
如果投影正常但它还不触发，那就是它还有别的判定条件。

### 已知边界

- 投影槽的等级恒为 1、复苏度恒为 0（要求复苏度阈值的被动可能仍不触发）
- 只投影**背包里**的物品；丢在地上/放箱子里不算「携带」
- 每 tick 最多重建一次映射，背包变动当 tick 就生效

## 18. 灵异交错：鬼会借用别人的杀人规律

新世界生成的厉鬼，除了自己的规律，还会随机"借"几条别人的判定。
条数按难度走：

| 难度 | 交错条数 |
|---|---|
| 和平 | 0 |
| 简单 | 2 |
| 普通 | 3 |
| 困难 | 4 |

随难度递增；要整体加码就把三个数一起 +1，常量只有 `GhostRuleCrossing.COUNT` 一处。

### 为什么单独开一个模块，而不是复用本源规律

本源规律是按 moduleId 单例的，一只鬼只能挂一份；而它的事件是
`attack_hit`（**物品**打人）。鬼要打人是 `attack_rule`（宿主自己判定）。

所以交错单独成模块 `smfsaddon:crossing`：

- 挂在鬼身上，监听 `attack_rule`
- 逐个问借来的影子"这人该不该死"，任意一个成立 → `allow()`
- **只 allow 不 deny**：交错是"多一条杀你的理由"，不是抹掉它自己的判断

### 顺带借「机制」，不只是「判定」

规律决定**该不该杀**，机制决定**用什么手段**。所以交错除了借鬼种，还会借 1~2 个机制模块：

| 难度 | 借来的规律 | 借来的机制 |
|---|---|---|
| 和平 | 0 | 0 |
| 简单 | 2 | 0 |
| 普通 | 3 | 1 |
| 困难 | 4 | 2 |

机制比规律少，因为一条机制顶得上好几条判定（踩头是一击必杀），
借多了会让交错变成"缝合怪"，玩家连它是什么鬼都认不出来。

**能借的机制只有三个**，写死在 `BORROWABLE_MECHANISMS`：

| 模块 | 为什么能借 |
|---|---|
| 踩人鬼 | 监听 `attack_rule`，鬼宿主上会触发 |
| 空间压制 | 监听 `nearby_player`，鬼有空间能力 |
| 鬼域在场 | 监听 `nearby_player`，同上 |

不能借的都记录在注释里：`door_bane` 只听 `item_use`（物品被使用，鬼用不上）、
`scapegoat` 需要"主人"、`native_rule` 和 `crossing` 是判定本身、`cornered` 拆开就失效。

**装错模块不会报错，只会静默不生效** —— 所以这里用白名单而不是"试一遍看能不能装"。

### 老鬼为什么不受影响

没交错过的鬼身上根本没有这个模块。`attack_rule` 上没有任何模块表态，
裁决保持 `ABSTAIN`，宿主回落它自己的老逻辑 —— 行为一个字节都不变。

### 两条工程约束

**影子实例必须缓存。** 一次判定要造 N 个影子（困难难度 5 个）。
老实现每次 `type.create()` 新的、用完 `discard()`，攻击一频繁就是 GC 灾难。
现在按 `(世界, 类型)` 复用同一个影子，只改坐标；世界切换和服务端停止时清空。
造不出来的类型记进黑名单，不再重试。

**候选池要预热。** 建池要试着造几百个实体。放在"第一只鬼生成的那个 tick"里
会卡一下，所以挪到 `SERVER_STARTED`：启动慢几百毫秒，换游戏中不卡。

### 已知的"白借"

有些鬼的 `shouldAttackPlayer` 依赖自身状态（鬼域是否展开、有没有目标、
是不是某个阶段），影子实例没有这些状态，判定永远是 false。

也就是说 4 条里可能有 1~2 条实际不生效。这不是 bug，是随机性的自然结果 ——
但排查时会误以为"交错没工作"，所以：

```
/ghostmodules check
```

不只列出借了哪几条，还会给出每条**判定次数与命中次数**：

```
✓ 交错 3 条
  · 门鬼     判定 0 次，还没判定过
  · 踩人鬼   判定 42 次，命中 9
  · 疫鬼     判定 42 次，命中 0  疑似白借（它的判定依赖自身场景）
```

判定过 5 次以上、一次都没命中的，标「疑似白借」—— 这比"造不出影子"更隐蔽，
因为影子造得出来、只是永远返回 false。

**为什么三条的次数常常一模一样**：本体每 tick 问一次"这人该不该杀"，
我们收到询问后要逐条问影子。三条都不成立时，每一问都会问满三条 ——
所以 161 次 = 这只鬼被问了 161 次（约 8 秒），三条各被问 161 次。
一旦某条命中，后面的就不再问了，次数才会出现差异。

统计按**宿主**分别记（`GhostRuleCrossing.HOST_STATS`），不放 NBT ——
判定是每 tick 的高频事件，写盘会把存档写烂。服务端停止时清空。

### 统计只用来观察，不用来筛选

曾经想过按"长期 0 命中"自动淘汰某些类型，撤掉了。原因是这条判据不成立：

- 玩家站着不动时，绝大多数规律本来就不该响（要潜行、要泡水、要作恶），
  但询问次数照样在涨 —— 淘汰掉的是**没被触发的规律**，不是坏掉的判定
- 更根本的是：没有谁知道一条规律的触发前提，**没人能证明它永远不会响**

所以统计只显示给人看，不干预抽样。要判断某条是不是真废了，
得结合 `docs/鬼能力分类.md` 里"判定读的是玩家还是它自己"这条轴人工判断。

### 为什么判定结果要缓存 0.5 秒

本体在 tick 里**对每个域内玩家**问一次"该不该杀"，实测三秒能问上百次。
每次询问都要问遍借来的类型，而其中四只鬼（门鬼、警官、敲门、垃圾）的
`shouldAttackPlayer` 内部会 `getEntitiesByClass` / stream —— 不缓存等于
每 tick 做几次实体扫描。

所以按 `(宿主, 目标, 类型)` 缓存结果，TTL 10 tick：

- 鬼的反应慢半秒，玩家察觉不到
- 实算次数直接降到 1/10（质检查询里「询问」与「实算」分开显示，能直接看出效果）
- 命中结果同样缓存，不会出现"忽打忽停"

## 附录 A · 踩坑清单

按编号记，方便以后搜。

1. **节流别用实体 `age`** —— 新实体从 0 开始，与上一条记录相减是负数，
   会导致刚刷出来的鬼长时间记不上。用世界时间。
2. **`PlayerEvents.getSpiritAttributes()` 返回副本** —— 改完必须整体
   `setSpiritAttributes()` 写回，否则不生效且不报错。
3. **`onInitialize` 混入要 `remap = false`** —— 模组自己的方法没有混淆映射。
4. **邻近扫描不能假设宿主是鬼** —— 原签名是 `GhostEntity`，
   方块宿主永远扫不到，且不报错。
5. **没有 `TickHost` 时 `tick` 恒为 0** —— `tick % interval == 0` 永远成立，
   会变成每 tick 全量扫描。
6. **yarn 1.20.1 没有 `DoubleArgumentType` / `StringArgumentType`** ——
   命令数值参数改用固定档位字面量。
7. **`./gradlew build` 在 Gradle 8.12 + 高版本 JDK 下会失败** ——
   `:test` 任务创建报 `Type T not present`，用 `remapJar` 代替。
8. **物品宿主的 `flush` 不能只看 dirty 标志** —— 模块可能被 `attach` 直接塞进容器、
   复苏值又是每 tick 在变，这两条都不经过 `markDirty()`。只看 dirty 的结果是
   模块数据一次都没写进 NBT，每次 `open()` 从空 NBT 重建，复苏值反复清零，
   表现为「挂了模块却毫无反应」。判据要用「有没有内容需要落盘」。
9. **服务端改了物品 NBT，客户端 tooltip 不会自动更新** ——
   `ItemStack` 的 NBT 改动不会触发同步。要让 tooltip 跟着变，
   得在写完后主动 `playerScreenHandler.syncState()`。
10. **MC 的 `Random` 是 `net.minecraft.util.math.random.Random`** ——
    不是 `java.util.Random`，`Entity#getRandom()` 返回前者。
11. **自定义槽位不写 `onClosed` 会吞物品** —— `SimpleInventory` 不归玩家背包管，
    关界面时没人回收就消失了。要在 `onClosed` 里 `insertStack`，满了就 `dropItem`。
    另外 1.20.1 里这个方法叫 `onClosed`，不是 `close`。
12. **移植成功的物品必须能看出来** —— 否则「没移植上」和「移植上了但没触发」
    在外部完全一样。任何带模块的物品都该显示承载条数，规律触发时也该有反馈。
13. **`Registries.X.get()` 找不到时返回默认条目** —— 实体注册表是 `DefaultedRegistry`，
    默认值是 `minecraft:pig`。直接 `get()` 会把不存在的鬼显示成「猪」。
    一律用 `getOrEmpty()`。
14. **命名空间不能写死** —— 别的附属的鬼在自己的命名空间下。写死 `smfs:` 有两个后果：
    本源规律建不出影子实例（**静默失效**），词条退回英文短名。要跨命名空间按路径找。
15. **`ItemStack#postHit` 返回 `void`** —— 写成 `CallbackInfoReturnable<Boolean>` 能编译通过，
    但运行时注入失败。注解处理器不校验处理方法签名，只能从 refmap 里看出返回类型是 `V`。
16. **`@Shadow` 拿不到继承来的 protected 字段** —— 会警告 `Cannot find target` 并在运行时失败。
    改用 mixin 继承父类，代价是构造器签名必须和目标类完全一致。
17. **`Map.ofEntries` 有重复键会在类初始化时抛异常** —— 不报编译错，运行时才炸。
18. **改代码要用能验证的方式** —— 字符串替换不匹配时会静默不改，导致「以为改了其实没改」，
    白测好几轮。改完要回读源码，或者直接在产物里搜关键字确认。
19. **数值放大后，固定偏移的惩罚会全部撞上限** —— 融合成本从 90 提到 3600 之后，
    `差值 × 0.05` 算出来上千，全部被 `min(12, ...)` 截断，缩放彻底失效，
    每次失败都是同样的满额惩罚。凡是「按差值缩放」的地方，都要问一句
    **数值涨十倍之后它还成立吗**；用比例（缺口/需求）就没这个问题。
