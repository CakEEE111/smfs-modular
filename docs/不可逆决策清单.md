# 不可逆决策清单

> 写给"要按最高标准做"的你。
>
> 这份清单只收录**一旦发版就很难改**的东西。代码写错可以重写，
> 数据结构定错、接口粒度定错，就要做存档迁移或让第三方插件全面失效。
>
> 建议在第一份内容发布前逐条过一遍。

---

## 一、存档结构

| 决策 | 当前值 | 反悔代价 | 保险 |
|---|---|---|---|
| 模块数据挂在实体 NBT 的哪个键 | `GhostModules` | 改名 = 所有已存档的鬼丢模块 | 已加版本号字段 |
| 模块数据条目格式 | `{Id, Intensity, Revival, Custom}` | 改字段名 = 丢数据 | 读档时缺字段走默认值 |
| 图鉴键格式 | `鬼类型\|规则ID → 次数` | 改成"规则级共享"要做迁移 | 已加版本号字段 |
| 图鉴存在哪 | 本体玩家数据 `smfsaddon_codex` | 换位置 = 所有玩家图鉴清空 | — |
| 方块宿主的 NBT 子树 | 方块实体根下的 `Modules` / `Plugins` | 改名 = 已放置的方块丢模块 | 已带 `v` 版本号 |
| 物品宿主的 NBT 子树 | 物品根下的 `SmfsAddonHost` | 改名 = 玩家背包里的道具丢模块 | 已带 `v` 版本号 |
| 本源规律的多鬼绑定格式 | `Custom.GhostTypes`（逗号分隔） | 改成数组会读不出旧绑定，已融的剑丢鬼 | 读取时兼容旧的单值 `Custom.GhostType` |

**已加的保险**：`GhostModuleContainer` 与 `RuleCodex` 写盘时都带 `v` 字段。
现在没用，但将来要做迁移时，`readNbt` 能据此判断"这是旧格式"，
而不是靠猜字段在不在。

## 二、命名空间与 ID

| 决策 | 当前值 | 反悔代价 |
|---|---|---|
| 模块 ID 前缀 | `smfsaddon:` | 改前缀 = 存档里的模块全部失效 |
| 规则 ID 格式 | `模块id/规则名` | 改名 = 图鉴记录全部对不上 |
| 图鉴条目的身份 | `(鬼类型, 规则ID)` | 改成按规则共享要做迁移 |

**硬规则**：模块 ID 和规则 ID 一旦发布，**永远不要改名**。
要改行为就换实现，不要换 ID。这是所有数据驱动系统里最容易犯、
后果最重的一个错。

---

## 三、宿主能力接口

| 决策 | 当前值 | 反悔代价 |
|---|---|---|
| 能力查询签名 | `<T> Optional<T> capability(Class<T>)` | 改签名 = 所有插件编译不过 |
| 能力集合 | `SpatialHost` / `EntityHost` / `GhostEntityHost` / `TickHost` / `PersistentHost` | 删能力 = 依赖它的插件失效 |
| 能力接口能否加方法 | 不能 | 加方法 = 第三方实现全部编译失败 |

**硬规则一**：能力接口一旦有第三方实现，就当成 published API，
加方法等于破坏性变更。要加能力就**新建接口**，不要去改老的。

**硬规则二**：宁可多建小接口，不要建大接口。
`EntityHost` 只有 `living()` 一个方法是对的 ——
如果当初把"能攻击""能受伤""有朝向"都塞进去，
将来做道具宿主时就被迫实现一堆没意义的方法。

---

## 四、模块与规则契约

| 决策 | 当前值 | 反悔代价 |
|---|---|---|
| 规则三方法 | `supports` / `canTrigger` / `onTrigger` | 改语义 = 所有规则行为漂移 |
| 裁决三态 | `ALLOW` / `DENY` / `ABSTAIN` | 去掉 `ABSTAIN` = 旧鬼行为全变 |
| 执行顺序 | 元规则 → 优先级降序 → 互斥去重 → 结算代价 | 改顺序 = 所有组合行为变化 |
| 模块单例约束 | 实现必须无状态 | 违反 = 多只鬼互相污染，且极难排查 |

**`ABSTAIN` 必须永久保留**。它是"新体系与旧鬼共存"的唯一支点，
一旦去掉，43 只本体鬼的行为会全部改变。

**"模块必须无状态"这条要写进文档、写进模板**。
它不会立刻出错，会在一百只鬼之后以"某只鬼的状态莫名共享"的形式炸出来。

## 五、事件集合

| 决策 | 当前值 | 反悔代价 |
|---|---|---|
| 事件 ID | `smfsaddon:tick` / `attack_rule` / `damaged` / `nearby_player` | 改名 = 规则 `supports()` 全部失效 |
| 事件是否带玩家 | `player()` 可空 | 去掉 = 图鉴失去观察者 |

**硬规则**：事件只增不删、不改 ID。要废弃就标 `@Deprecated` 并保留。

---

## 六、还没定、但迟早要定的

这几条现在不定也活得下去，但会在某个时刻变成硬约束：

1. **规则知识是否跨鬼共享**——现在按 `(鬼, 规则)` 记，玩家在 A 鬼身上学会的规律，
   到 B 鬼身上要重新学。要改成跨鬼共享，就得改图鉴键格式 + 做迁移。
2. **装配表的格式**——将来"哪只鬼由哪些模块组成"要变成 JSON，
   那么 JSON 的 schema 一旦发布就不能乱改。
3. **同步策略**——模块状态现在只在服务端，客户端表现靠实体已有的 DataTracker。
   一旦有插件要在客户端读模块状态，就要定一套同步协议。

---

## 给未来的自己

三条判据，遇到犹豫时用：

1. **这个字段，两年后还放得下吗？** 放不下就现在加上 `v` 字段和默认值。
2. **第三方会实现这个接口吗？** 会，就当它是公开 API，只增不改。
3. **删掉这个东西，旧存档会怎样？** 会丢数据，就保留它并标废弃，别删。
